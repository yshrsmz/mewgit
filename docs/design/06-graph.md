# 06. graph: tig 風レーン描画

## 責務

コミット列（topo-order）を受け取り、各行のレーン割り当てと罫線セルを生成する。描画はしない（セルの列を返し、`ui` が文字と色に変換する）。

**グラフ先頭の WIP 行はこの層を通らない。** コミットではないので `Commit` を組めず、
偽のものを `extend` に流すとレーンの状態（次に待つ oid）が壊れて以降の行がずれる。
`ui` が `◇` の 1 行を自分で描き、罫線は繋がない（07 の「Graph ペイン」）。HEAD の行へ
縦線を伸ばすには中間行に `Vertical::Through` を差し込む必要があるうえ、
`TOPOLOGICAL | TIME` では HEAD が 0 行目とは限らず、最初のページに入っているとも
限らない（下の「ページングとの整合」）。

## データ構造

```rust
pub struct Lane { oid: Oid, color: ColorId }        // レーンが次に待つコミットと、その色

pub struct LaneState {
    lanes: Vec<Option<Lane>>,                       // 左から順。None は空きレーン
    next_color: u16,                                // 次に採番する ColorId
}

impl LaneState {
    /// 続きのコミット列に割り当て、行を返す。状態は末尾行の直後まで進む。
    pub fn extend(&mut self, commits: &[Commit]) -> Vec<GraphRow>;
}

pub struct ColorId(pub u16);        // usize ではなく u16。Cell が 32 バイト → 8 バイトになる

pub struct GraphRow {
    pub oid: Oid,
    pub lane: usize,                    // このコミットの列
    pub cells: Vec<Cell>,               // 左から順に
    pub color: ColorId,
}

pub struct Cell {                       // 1 マス。縦成分と横成分は独立に立つ
    pub vertical: Vertical,
    pub horizontal: Horizontal,
}

pub enum Vertical {
    None,
    Through(ColorId),                       // 上下に貫く
    Up(ColorId),                            // 上から来てこの行で終わる
    Down(ColorId),                          // この行から下へ伸びる
    Commit { color: ColorId, merge: bool }, // コミット本体。merge なら親が 2 つ以上
}

pub enum Horizontal {
    None,
    Left(ColorId),                      // 左へ伸びる
    Right(ColorId),                     // 右へ伸びる
    Both(ColorId),                      // 通り抜ける
}
```

`app` が呼ぶのは `extend` だけ。行の作り方を `graph` の中に閉じておくことで、
アルゴリズムを入れ替えるときに `app` を触らずに済む。

### なぜ「縦 × 横」なのか

1 マスに 1 文字を割り当てるので、`ui` は上下左右のどこに線が伸びているかを知る必要がある。
`BranchOut` / `MergeIn` のような「向き」の名前だと、`╮`（上が無い）と `┤`（上から続く）、
`╯` と `┴`（横線がさらに右へ抜ける）を区別できず、`ui` が隣の行を覗いて推測することになる。
それは「行の作り方を `graph` に閉じる」に反する。縦と横を別に持てば、文字は
(縦, 横) の組から一意に決まる。

| | `Horizontal::None` | `Left` | `Right` | `Both` |
|---|---|---|---|---|
| `Vertical::None` | 空白 | `─` | `─` | `─` |
| `Through` | `│` | `┤` | `├` | `┼` |
| `Up` | `╵` | `╯` | `╰` | `┴` |
| `Down` | `╷` | `╮` | `╭` | `┬` |
| `Commit` | `●` / `○` | `●` / `○` | `●` / `○` | `●` / `○` |

横線は右だけでなく**左にも走る**。`c.lane` より左のレーンが `p2` を待っている場合
（feature ブランチで main を取り込んだ典型）に起きる。

## アルゴリズム（1 行ずつ、状態を引き継ぐ）

各コミット `c`（親 `p1..pn`）について:

1. `lanes` から `c.oid` を待っているレーンを全部探す
   - 0 個: 新しいレーン（右端）に置く。ルート側の新規ブランチ先頭
   - 1 個以上: 最左を `c.lane` とし、残りは `Up` + 横線で `c.lane` へ引いて空ける
2. 親の配置
   - `p1` を `c.lane` に置く（同じ色を継承）。親が無ければ `c.lane` を空ける
   - `p2..` は既に待っているレーンがあればそこへ横線で接続（そのレーンは `Through` のまま）、
     なければ右側の空きレーンに `Down` で置いて横線をつなぐ。新しい色を割り当てる
   - 同じ行で空けたレーンは `p2..` の置き場に使わない。使うと「ずっと続いていたレーン」に
     見えてしまう。空き判定は**その時点の** `lanes` を見て、合流で空けたレーン
     （手順 1 の待ちレーン）だけを除く。行に入る前の状態を見てはいけない。
     オクトパスマージで `p2` を置いた直後のレーンが空きに見え、`p3` が同じレーンを
     上書きしてしまう
3. 空になった末尾レーンを詰める（中間の空きは残し、次のコミットで再利用）
4. `cells` を `lanes` の長さ分生成する。末尾の空セルは落とす

`p1` を置くとき、他のレーンが既に同じ oid を待っていても畳まない。合流はその親の行で
起きる（そこで `waiting` が 2 個以上になる）。

## 色

- ColorId は `p1` 連鎖で継承し、分岐時に新規採番（単調増加、`wrapping_add`）
- 実際の色は `ui` で `ColorId % palette.len()` に写像する。`graph` は palette の長さを
  知らないので、隣接レーンの色が衝突しないようにする責任は持たない
- **MVP では隣接レーンの同色を許容する。** 避けるなら `LaneState` に palette の長さを
  渡して採番時に左右を見るしかなく、`graph` が `ui` の都合を持つことになる。
  実際に見づらいと判った時点で、どちらの層でやるかを決め直す
- 横線の色は到達先レーンの色。線が重なるマスは 1 色しか出せないので、先に引いた
  ほうを残す。引く順は 合流線 → `p2..` の順（親の並び順）。距離順ではない

## ページングとの整合

- `LaneState` は末尾の 1 個だけ保存する。追加ページ計算はそこから再開する。
  行ごとに持っても読む場面が無い（上方向は再計算不要、ref 変更時は先頭から再計算）ので、
  行数ぶんの `Vec<Option<Lane>>` を抱えない
- 上方向のスクロールは既に計算済みなので再計算不要
- ref の変更（fetch 後）は先頭から再計算する。数千行までは 10ms 程度で終わる想定

## ラベル

- `RefIndex`（02）から `oid → Vec<RefLabel>` を引き、`GraphRow` の右に並べる
- 種別ごとの見た目: ローカル `[main]`、リモート `{origin/main}`、タグ `<v1.0>`、HEAD は太字、PR は `#123` を PR 状態の色で
- 幅が足りないときはラベル → summary の順で省略

## ASCII フォールバック

`config.graph.ascii = true` のとき、`ui` 側で罫線を ASCII に置き換える
（`│→|`、`─→-`、`╮ ╭→\ /`、`╯ ╰→/ \`、`├ ┤ ┬ ┴ ┼→+`、`● ○→* o`）。
`graph` 層は文字を持たないので、置換表は `ui` にしか無い。

**このキーはグラフ以外の記号にも効く。** Branches ペインの ahead / behind
（`↑ ↓ → ^ v`。07）が最初の例で、選ぶところは `ui::pick_charset` の 1 本。
キーが `[graph]` の下にあるのは最初の利用者がグラフだったからで、意味は
「この端末が非 ASCII の記号を出せるか」（既定は locale から決まる。08）。
`↑`（U+2191）/ `↓`（U+2193）は下の罫線と同じ East Asian Ambiguous 幅なので、
曖昧幅を全角に描く端末でずれるのも同じ。

罫線の文字（U+2500 台）と `●` `○` は East Asian Ambiguous 幅で、曖昧幅を全角として
描く端末（`ja_JP` などのロケールで iTerm2 の "Treat ambiguous-width characters as
double width" を有効にした場合など）では 1 マスが 2 桁になる。ratatui は 1 桁として
数えるので、その端末では Oid 以降が右にずれ、ペインの右枠が画面外へ出る。
逃げ道は `ascii = true`。ロケールが UTF-8 でも起きるので、下の自動判定では拾えない。

端末が UTF-8 かどうかの自動判定はまだ入れていない。入れるときは `Config::load()` が
`LC_ALL` / `LC_CTYPE` / `LANG` を見て `graph.ascii` の既定を決める（08 の「読み込み順」
手順 4。`ui` は環境変数を読まない）。M6 のタスク。

## テスト

- 直線 / 単純分岐 / マージ / オクトパスマージ / 複数ルート / 左向きマージ（`p2` が
  `c.lane` より左のレーンで待つ）の固定ケースを検証する。読みやすさのため
  テスト専用のレンダラで文字列に落として比べ、生の `Vec<Cell>` の期待値とも
  1 ケース突き合わせる（レンダラ自体が間違っていても気付けるようにするため）
- 同じコミット列を途中で 2 つに割って `extend` を 2 回呼んだ結果が、1 回で呼んだ結果と
  一致すること。「ページングとの整合」の主張はこれで固定する
- (縦, 横) の全 16 通りが期待どおりの文字になることは `ui` 側の単体テストで固定する
  （`mewgit-tui` の `ui::lanes`）。`graph` のテスト用レンダラと同じ表なので、
  `ui::panes::graph` が両者の突き合わせを 1 ケース持つ
- 実履歴（`TestRepo`）に対する不変条件を確認する。「第 1 親のレーンは子より右に
  ずれない」「同じレーンなら色を継ぐ」「各行のコミットのマスは本体（`Commit`）である」の
  3 つ。合流では最左の待ちレーンに寄るので「同じレーンに現れる」までは言えない。
  `git log --graph` の出力と文字単位で比べることはしない（git 側の整形規則に
  追従する意味が無い）
