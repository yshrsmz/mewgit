# PR を作る前に

`gh pr create` の前に、CI 相当のチェックに加えて必ずこの順で実行する。

1. `/simplify` — 重複・冗長・不要な抽象を削る。指摘の適用まで含む
2. `/code-review medium` — バグを探す。指摘があれば直してから次へ。
   **`high` から下げた**（2026-09-22 に決めた）—— あちらは網羅を広く取るぶん確度の
   低い指摘も混じるので、**採らない判断とその裏取り**（下の「false positive」）が
   PR ごとに積む。`medium` は確度の高いものだけを出す
3. 修正が出たら CI 相当のチェックを流し直し、別コミットとして積む（amend しない）

どちらも指摘ゼロなら何もコミットせずに PR へ進む。レビュー指摘に「直さない」判断をした
場合は、その理由を PR 本文に書く。

**「次のタスクへ送る」と書いたら `docs/plan.md` に未チェックの行を作る。** 設計書と
コメントは**理由の置き場で、着手の入口ではない** —— そのコンポーネントを触る人しか
読まないので、送ったつもりの穴に着手する機会が来ない。行には**塞ぐのに何が要るか**まで
書く（既存のタスクに相乗りさせるなら、そのタスクの行に足す）。#73 では残した穴 2 つを
M4 と M6 の行にしてある。
**語は「送る」に限らない。PR 本文の「残した穴」「見送り」「範囲外」「〜が要る」も全部
これに当たる。** 後続のセッションはマージ済みの PR を読みに行かないので、PR 本文にしか
無いものは無かったことになる。**先に plan.md の行（と理由を置く設計書）を書き、PR 本文は
それを指すだけにする。** #120 では「外で終えた直後の 1 回目は断られる」「対象ブランチの
改名は名前が消える」「テストの共通化を見送り」を PR 本文にだけ書いて出し、ユーザーに
「後続のセッションは古い PR なんて見に行かない」と指摘された。**しかも行に送る前に
送り先の前提を叩いていなかった** —— M6 の監視の行は `.git/HEAD` を見る形で、
cherry-pick / merge / revert の終わりでは HEAD の mtime が変わらない（実測）ので、
そのまま送っても塞がらなかった。**送り先の行が本当に穴を塞ぐかを数えてから送る**

**「false positive」「対応不要」は裏を取ってから書く。** 理由の欄が埋まっていることと、
判断が正しいことは別。指摘が言う失敗の筋道（どの入力で・どの状態で・何が起きるか）を
**実際に踏んでみて、踏めないことを確かめてから**採らないと決める。確かめ方は対象ごとに
違うので `.claude/rules/verifying-assumptions.md` の表を使う（一時リポジトリ・pty・
依存クレートのソース）。**PR 本文には結論ではなく踏んだ形を書く** ——「false positive」
ではなく「この経路は `<関数>` が手前で断るので組めない（一時リポジトリで確認）」。
踏めるかどうか判らなかったときは、**「確かめられなかった」とそのまま書く**
（同じ rules の「確かめられなかったときは『確かめていない』と明記する」）。
**`medium` に下げても緩めない。** 確度の高いものだけが出るぶん、**裏を取らずに
「false positive」と書いたときに外れている確率は上がる**。

**指摘が当たっていることと、指摘が添えた直し方が当たっていることは別。** 上は
採らない側の裏取りで、こちらは**採る側**。#98 の「`branch.<name>.remote` は push 先では
ない」は正しかったが、同じ指摘が添えた直し方（`merge` が `refs/heads/<name>` と違うかで
判別する）は**その指摘自身が主例に挙げた手順で外れた**（`checkout -b fix bob/fix` の
`merge` は `refs/heads/fix`）。**一時リポジトリで踏んだのは指摘の筋道のほうだけ**で、
直し方は別に叩く必要があった。**採ると決めたら、その直し方でも同じ手順を踏み直す。**

**この 2 つを通すのは Rust コードを含む PR だけ。** docs や CI 設定しか触らない PR では
省く。`/simplify` の 4 観点（既存ヘルパの再利用・冗長な状態・無駄な計算・修正の深さ）は
どれもコード前提で、Markdown や YAML には当たらない。省いたことと理由は PR 本文に書く。

**レビューのエージェントは計測のために一時的にコードを書き換える。** #94 では efficiency
観点が確保回数を数えるモジュールを足して測り、`cp` で戻した（その値が指摘の根拠になって
いる）。**並列で回している別のエージェントがその一瞬を見て「作業ツリーが汚れている」と
報告することがある**ので、**回す前にコミットしておき**、その種の指摘は自分で
`git status` を見て裁く。

**回しているあいだはコミットを積まない。** 上は作業ツリーが汚れる話で、こちらは
**レビュアーの基準コミットが動く**話。#101 では `/code-review` を回している最中に
修正を 1 本積んだので、指摘が**古い木の行番号**で返り、現在の HEAD に当て直す手間と
「もう直っている指摘」の仕分けが出た（レビュアー自身も冒頭で断っていた）。**待てない
修正を積んだら、返ってきた指摘を先に当て直してから読む。**

どちらもバックグラウンドのエージェントとして走り、完了はハーネスが通知する。待機のために
no-op のコマンドを回さない（`echo waiting` の空回しなど）。ターンを終えて通知を待つ。

**エージェントが失敗したら、自己レビューで代替せずに立て直す。** セッションのレート上限で
落ちることがあり、エラーにリセット時刻が出る。自分で書いたコードを自分で見直しても
独立性が無く、この手順が効いている理由そのものが失われる。時刻を過ぎてから、落ちた
エージェントを同じ観点で立て直す。

**`/code-review` は新規コンテキストのエージェントで回す。** スキルとして起動すると
**fork**（親の会話コンテキストをそのまま引き継ぐ形）になり、**書いた本人の言い訳ごと
引き継いだレビュアー**ができる。`/simplify` のほうは `general-purpose` で起動するので
元から独立している。**この違いは症状で見分けられない** —— fork でも指摘は出るし、
確度も高そうに読める。#78 では fork の `high` と自分でのインライン `medium` を
通したあとに新規コンテキストで回し直したら、**3 件とも「ブランチ内の主張が嘘」**
（見張りが経路を踏んでいない・守りの根拠に書いた文が事実と違う・直した節の隣に前提が
生き残っている）が出た —— **どれもコンテキストを共有した側が構造的に素通りする種類。**
リポジトリとブランチ名だけを渡し、**自分の判断や理由は 1 つも渡さない**。
「コメントや doc が『この状態には到達しない』『これは安全』と主張している箇所を
反証しろ」まで指示に入れる（拾われるのはそこなので）。

**2 つの指摘が逆を向くことがある。実害がある側を採る。** #38 では `/simplify` の
「将来 `Range` を出したときにガードが外れる」という一般化を入れ、`/code-review` に
その場の回帰（コンフリクトの案内が別の文言に化ける）を拾われた。**将来のための
一般化は、いま踏める腕が無ければ「テストで踏めない状態をコードに入れない」に負ける。**
採らなかった側は、送り先と理由をコメントか設計書に書いて次のタスクへ送る。

**ここまで通したら、`git push` と `gh pr create` は確認を取らずに実行する。**
「PR を作りますか」と聞かない —— この手順を通すこと自体がタスク完了の形なので、
そこで 1 往復増やしても判断材料は増えない。確認が要るのは**手順から外れるほう**
（force push、`main` への直 push、既存ファイルの削除。`.claude/rules/asking-questions.md`）。

## 実績と、当たる指摘の類型

**#6 以降すべてで両方から実際に指摘が出ている。** 形式的な手順ではないので省略しない。
**新規コンテキストで回した `/code-review` は、#78 以降ほぼ毎回ブランチ内の主張の嘘を
出している**（#118 でも 3 件すべてが「記述が事実と違う」だった）。当たるものは次の
類型に落ちる。どれも**書いた本人のコンテキストでは「そう書いたのだからそうだろう」で
素通りする**種類（PR 番号は根拠。並べ足さない）。

- **見張りが狙った経路を踏んでいない** —— #90 / #96 / #101。どれも変異で実証された
- **自分が書いた断定が嘘** —— #96 / #98 / #101 / #107 / #118（実測の fixture が
  狙っていない理由で止まっていた。`.claude/rules/verifying-assumptions.md`）
- **設計の穴。`/simplify` の 4 観点では出ない** —— #101 の非同期の到着順。
  **品質が緑でも設計に穴は残る**

**レビューの指摘も変異で裁く。** #82 では `/simplify` の altitude が「代替が無く
カバレッジを失っている」を 4 件出したが、**実装を壊したら 4 件とも生存側が落ちた**
（生存側の取り違えと、`"Branches"` での grep が `"Branches (40)"` に当たっていなかった
もの）。**観点を疑うのではなく、自分の削除と相手の指摘を同じ変異に掛ける。**

**altitude を軽く見ない。** #96 では 4 観点のうち altitude が最も深い指摘を当てた
（Reuse と Simplification が同じ場所を別の言葉で指していて、**観点が重なった所が
いちばん実害のある指摘**だった）。#118 では altitude が**ブランチより前に設計書へ
書いてあった決定**（03 の「`ExecFinished` に束ねる」）を覆す案を出し、採った ——
**設計書にあることは指摘を断る理由にならない**。覆すかどうかはユーザーに聞く。
**2 観点が独立に同じ再現を出したら、まず疑う**（#89 で効率と高度が同じ再現を出した）
