# 設計書を直すときの教訓

`CLAUDE.md` の「まず読むもの」の続き。設計書（`docs/`）を書く・直すときに読む。

**揃えるのは文書と文書のあいだだけではない。同じ 1 本の中も通しで読む。** 条件や
引き金を 1 つ増やしたら、その文書内の「◯◯のとき」を grep する（**「◯つある」は
そもそも書かない**。コーディング規約（`rust-coding.md`）の「離れた場所に…『いま N ある』を書かない」）。#54 では
Diff ペインを巡回の候補から落とすようにしたのに、**01 の中だけで 3 箇所が古いまま
残った** —— 座り直しの引き金（「WIP 行を出入りしたとき」に条件が 1 つ増えていた）、
「どちらの選択でも候補にあるのは 3 つ」という数、頼み直しが無いときに残る文言。
**節をまたぐと、直した節の隣で前提が生き残る。**

**同じ判断の理由を設計書・doc コメント・テストコメントの 3 箇所に書いたなら、直すときの
grep 対象にテストコメントも入れる。** #42 では、レビューを受けて 07 の理由を書き換えた
のに、同じ理由を書いたテストコメントだけが古いまま残った。テストコメントは設計書の語で
検索しても出にくい。

**教訓として書かれた項目は「踏んだ形」であって結論ではない。根拠に引く前に PR 番号から
コミット本文を読む。** `CLAUDE.md` も `handover.local.md` も「こう間違えた」を書いて
いるので、そのまま引くと**意味が反転する**。#61 では handover の「#21 は設計書 03 から
`Runner.git_bin` を『要求が無い』と判断して消した」を結論と読んで `gh` のパスを直書き
したが、それは**拾われた誤りのほう**で、#21 の本文は「`Runner` に `git_bin` を**戻し**、
`config` の `general.git_bin` から渡す形にした」だった。おかげで `general.gh_bin` が
黙って死に、#21 が塞いだのと同じ穴を開け直した（`/simplify` が拾った）。
**`git show <sha>` は 1 コマンドで、引用が逆を向いていないかはそれでしか判らない。**

**逆に、判断を次のタスクへ送るときは、挙げた候補が他の設計書の制約で全滅していないかを
数える。** #59 では 04 に「`resolve(api: &GithubClient)` は成り立たない」と書いて候補を
2 つ挙げたが、**どちらも 00 のレイヤー則（`github` は `auth` の上段）で上向きになり、
最初から死んでいた**（`/simplify` が拾った）。トークンが 1 本という目に付く理由だけを
数えて、**先に効く制約を数えていなかった**。送り先の設計書に書く前に、その形が
他の設計書で許されるかを確かめる。

**設計書が「そのタスクで決める」と送った判断は、着手時に `docs/design/` 全体を grep する。**
#47 では 02 の「`Branch.upstream` から push の `-u` を決めない」（短縮名の `None` には
4 つの理由があるので、`branch.<name>.merge` を読んで決める）を破った実装を書き、
`/simplify` に拾われた。**破ったことは `git_read` を一度も開かずに書けてしまう** —
送り先が書いてあるのは送った側の設計書で、実装するときに読むのは受け取る側だから。
`-u` や `expected` のように「M3 で決める」と名指しされた語で探す。
