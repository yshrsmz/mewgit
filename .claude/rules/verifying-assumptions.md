# 推測で断定しない

- **外部の振る舞いを「できない」「こうなっている」と書く前に、手元にある実物で
  確かめる。** 設計書やコメントに書いてしまうと、外した前提の上に実装が積む。
  確かめられなかったときは「確かめていない」と明記する。
- **書く先は設計書とコメントだけではない。ユーザーへの報告の中の断定も同じ。**
  そこで断定すると、**回り道を正当化する根拠**になってユーザーが検算する側に回る。
  #75 では「`cargo fix` は lib ターゲットの判断でテスト専用の import まで落とすので
  使えません」と書いて疑われ、測ったら答えは「使えない」ではなく**「ヘッダがテスト
  専用の import を抱えている形でだけ壊れる」**だった —— 道具ではなくこちらの形が
  壊れており、**ヘッダを `cargo fix` に切り詰めさせる**のが正解だった。
  **断定が手順を曲げているときほど、先に叩く。**
- **逆に、設計書に既に書いてある「こうすれば塞げる」「こうなる」は、着手時に自分で
  叩く。** 上は書き手側、こちらは読み手側。**実測の根拠（表・PR 番号・実際に叩いた
  コマンド）が添えられていない断定は、書いた時点で確かめていない。** #56 では 03 の
  「キャンセルは `kill_on_drop`」を叩いたら、あれが送るのは SIGKILL なので git が
  sigchain の後始末をせずに死に、**`index.lock` が残って以後の書き込みが全部落ちる**
  ことが判った（設計書は「子プロセスを kill する」としか書いていなかった）。叩いた
  結果は設計書に表として残し、次に読む人が実測済みを見分けられるようにする。
- **実測を残すときは数そのものを残す。**「遅くなる」「大きい」に言い換えない ——
  次に読む人が判断できるのは数のほうで、言い換えたものからは元の値に戻れない
  （「起動 0.82 秒 → 2.04 秒」「境目は 30 本 × 80x14」）。**これは「離れた場所に
  『いま N ある』を書かない」（`.claude/rules/rust-coding.md`）の例外側**で、過去形の記録なので腐らない。
- 確かめる手段は対象で違う。

| 対象 | 確かめ方 |
|---|---|
| git の振る舞い | `tempfile` / `env -i` の一時リポジトリで実際に叩く。**実測済みの表は設計書にある** —— unstage / 切替 / `git apply` の効き方とコンフリクトが stdout に出ること（03）、`switch` と hook（07）、`switch --create` の追跡設定（05 の PR チェックアウト）、既定リモートの規則（04）、進行中操作のファイル（02） |
| 端末の振る舞い・起動コスト | pty で流して画面を復元する（`.claude/skills/pty-check/SKILL.md`）。時間は `time` で測る |
| git がサブプロセスに何を渡すか | `core.sshCommand` にダンプ用のスクリプトを噛ませて argv を見る（`git -c core.sshCommand='sh dump.sh' ls-remote <url>`） |
| ブラウザを開くコマンドが何を渡すか | `BROWSER`（`gh` は `GH_BROWSER` も見る）にダンプ用のスクリプトを置いて argv を見る。**窓は開かない**（`BROWSER="sh dump.sh" gh browse 1 -R <host>/<owner>/<repo>`） |
| 手元のツールが内部で何をしているか | バイナリを `strings` に通して grep する（設定ファイルに何を書くか、どのシーケンスを送るかが読める） |
| ツールが設定ファイルに**実際に何を書くか** | 一時リポジトリでそのツールを走らせ、`git config --list --local` を読む。`strings` は書きうる字は見せても、**どの値が入るかは見せない**（`gh pr checkout` は `branch.<name>.remote` にリモート名ではなく **URL** を書く。実測 2026-09-20、gh 2.101.0） |
| 他の TUI がどう並べているか | `script` + `stty` で実機を撮る（`.claude/skills/pty-check/SKILL.md`）。**`q` で終わると復元シーケンスまで録れる**ので `ESC[?1049l` の手前で切る。`scripts/screen.py` は部分再描画するアプリだとフレームが混ざるので、必要なら仮想画面を自前で起こす。スピナーの桁は生の `ESC[<行>;<桁>H` から読む |
| 依存クレートの挙動 | `~/.cargo/registry/src/*/<crate>-<version>/` のソースを読む。ドキュメントより実装が正しい |
| ある操作が GitHub API を何往復するか | pty で流し、**1 つのプロセスの中で**ヘッダの `[api: N]` が**落ち着いた値**だけを録画から拾う。罠が 2 つ（下） |
| 手元に無いプラットフォームでのビルド | 依存更新だけを積んだ draft PR を立てて CI を回す。手元は macOS しか無い |

- **`[api: N]` の罠は 2 つ。** #96 で「`r` 1 回の往復は 5」と書いて外した。
  **(1) 起動をまたいだ差では測れない** —— `auth::resolve` の probe は使い捨ての
  クライアントで叩くので残量をヘッダに出さず、次の起動の初期値がその手前で減って
  いる（自分が検証中に叩いた `gh` も同じ理由で混ざる）。**(2) ヘッダは桁ごとに
  部分再描画される** —— 生の録画から 4 桁の数を拾うと、書き換わる途中の値
  （`4079` → `4100` → `4190`）が混ざって 1 桁違う数が並ぶ。**次に値が変わるまで
  一定の文字数そのままだったものだけを採る**と、`4314` → `4310` のように 1 回ぶんが
  そのまま出る（正しくは 4 = 一覧 1 + 集計 3）。**往復数を減らす / 増やす判断の
  根拠にする数なので、ここを外すと設計の判断ごとずれる。**
- **ビルドできるかどうかが方針そのものを左右するなら、コードを書く前に叩く。**
  #59 では `rustls`（= aws-lc-rs）を選ぶ根拠が「`aws-lc-sys` の build.rs が Linux で
  通ること」で、**通らなければ feature の決定ごとやり直し**だった。手元は macOS しか
  無いので、依存更新だけの draft PR を先に立てて CI を回してから本体を書いた。
  **「GitHub の runner には cmake が入っているはず」で進めない。**
- **「その環境では区別できない」と書く前に、区別している実例を探す。** 実例が動いて
  いるなら、区別できないのではなく別の仕組みを使っている。
- **「効かない」と書く前に、効いた結果がどこに出るはずかを数える。** 上の姉妹形。
  道具が黙っているとき、壊れているのは道具ではなく**こちらの期待した行き先**のことが
  ある。`CLAUDE.md` は長らく「pty では `Tab` が効かない」と書いていたが、実際には
  効いていて、**巡回順の 1 つ目が期待と違っていた**だけだった（`Tab` 1 回で
  Worktree に居ると思って `s` を押していた。正しくは 3 回）。**「無反応だった」は
  観測で、「効かない」は結論** —— 結論を書く前に、効いたなら何がどう変わるはずかを
  実装から数える。
- **外部ツールの「アクティブ」「既定」は、どの操作に対してのものかを数える。**
  表の「ツールが設定ファイルに実際に何を書くか」の**読む側**の版。#110 では
  `gh auth status` の `active` を「`gh auth refresh` の相手」と読んだが、あれは
  **環境変数のトークンを含む**アクティブで、`GITHUB_TOKEN` を export していると
  keyring 側が全部 `active: false` になり、refresh の相手（設定上のアクティブ）と割れる。
  **手元の gh が環境変数を export していたのに**、叩いたのは `active` の表示だけで、
  案内する操作（refresh）の相手を叩かなかった。**案内する操作そのものを、同じ環境で
  叩く**
- **有効化・問い合わせの類は、効かない環境での待ち時間まで測る。** 応答しない相手を
  待つ実装は、対応していない環境ほど遅くなる。
- **「状態に届いている」と「画面に出ている」は別。** 自分の実装が「UI まで届けた」と
  書く前に、描く側まで辿る。#42 では `push_notice` に argv と stderr を渡したことを
  もって設計書に「git が断れば stderr がそのまま案内になる」と書いたが、ステータスバーは
  要約行しか描いておらず、**その記述を根拠にした「手前で判定しない」の半分が
  未実装だった**。渡した引数を見て「届いた」と読まない。
- **裏返しも同じ。「何も出ない」も確かめてから書く。** #78 では `git config --unset` が
  **exit 5 で stderr が空**なのを実測したところまでは合っていたのに、そこから
  「だから通知には何も出ない」と**辿らずに書いた**。実際は `exec_finished` が `Err` を
  必ず通知に積むので、**argv だけの赤い通知は出る** —— 出ないのは理由のほうだった。
  しかもその文は守りを入れる根拠として doc コメントと設計書の両方に置いたので、
  **実際より強い理由で守りを正当化していた**。外の世界の実測（exit と stderr）から
  自分の UI の挙動を推論したら、その推論も同じように叩く。
  #90 でも同じ形を踏んだ —— ヘッダを実測したところから「クライアントは残量を採らない」と
  書いたが、正しくは「運ぶ経路が無い」だった（確かめたのは外の世界で、結論は自分の側）。
- **状態を作る実測は、その状態が狙った理由で起きたかまで確かめる。** #118 では
  「exec の失敗で止まった rebase」を `git rebase -x false main` で作ったつもりが、
  fixture の 1 つ目の pick が `main` とコンフリクトしていて、**見ていたのはコンフリクトで
  止まった形**だった（`done` の最終行が `pick` だったのはそのため）。そこから「exec は
  失敗すると todo に戻される」と書き、`/code-review` が叩き直して外れた。**止まった・
  失敗した、を見る実測では、止まった理由（`git status` の見出し、unmerged のファイル）も
  一緒に読む**
