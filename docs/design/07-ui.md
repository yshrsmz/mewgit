# 07. ui: 画面・ペイン・モーダル・キーバインド

## レイアウト

目標の形は GitKraken に寄せる。**左の広い領域が「グラフ または diff」、右の狭い領域が
「いま左で選んでいるものの中身」**という 2 列で、左右のどちらも中身が入れ替わる。

```
┌ owner/name  main ↑1 ↓0   [gh: user_shortcode @ github.com]  ⟳ fetch ─┐
│                                   │ Working tree (3)                  │
│  Graph                            │  Staged                           │
│  ◇ WIP (3)                        │   M src/main.rs                   │
│  ● [main] {origin/main} Add ...   │  Unstaged                         │
│  │ ● <v1.0> Release              │   M src/graph.rs                  │
│  ├─╮ Merge feat/y                 │  Untracked                        │
│  │ ● Fix ...                      │   ? notes.md                      │
│  ● │ ...                          │                                   │
├───────────────────────────────────┴───────────────────────────────────┤
│  REBASE 3/7  10:03:26 変更のないファイルは stage できません            │
│ j/k:移動 Enter:差分 s:stage u:unstage x:破棄  ?:help q:quit            │
└───────────────────────────────────────────────────────────────────────┘

右でファイルを選んで Enter → 左が Diff に差し替わる（Esc で戻る）

┌ owner/name  main ↑1 ↓0 ────────────────────────────────────────────────┐
│                                   │ Working tree (3)                  │
│  Diff: src/main.rs                │  Staged                           │
│  @@ -1,4 +1,6 @@ fn main() {      │   M src/main.rs                   │
│   fn main() {                     │  Unstaged                         │
│  -    println!("old");            │   M src/graph.rs                  │
│  +    println!("new");            │  Untracked                        │
│                                   │   ? notes.md                      │
├───────────────────────────────────┴───────────────────────────────────┤
│                                                                       │
│ j/k:移動 s:stage u:unstage x:破棄 Esc:戻る  ?:help q:quit              │
└───────────────────────────────────────────────────────────────────────┘
```

- **左（幅 60%）は Graph か Diff のどちらか。** `focus == Pane::Diff` のあいだだけ Diff。
  差し替えであって分割ではないので、**グラフに使える領域の大きさは変わらない**
  （`ui::graph_rows` と `Msg::Layout` に手を入れずに済む。01 の「グラフの行」）
- **右（幅 40%）は上が Branches、下が「左で選んでいるものの中身」。** 下は
  「WIP 行を選択中 → Working tree、コミットを選択中 → そのコミットの詳細
  （メッセージ + 含まれるファイル一覧）」。**上の Branches は左の選択で入れ替わらない。**
  ブランチ一覧はグラフで何を選んでいるかと無関係だから。**上は `Branches | Stash | PRs`
  のタブ**（下の「右上のタブ」）
- 最上部: ヘッダ。リポジトリ名とアカウントと GitHub API の残量、右端に**実行中
  ジョブのスピナー**（下の「ヘッダ」）
- 最下部: **フッター 2 行**。1 行目に進行中操作と直近通知、2 行目にフォーカス中の
  ペインのキーヒント（下の「ステータスバー」）
- **上の図は幅を詰めて描いている。** 実際に 2 列に割るのは幅 100 から（下の「狭い端末」）

### 目標の形への割り方

**どこまで入ったかは `docs/plan.md` のチェックが持つ**（ここに状態の表を置いていたが、
チェックと 1 対 1 の写しだったので消した）。ここに残すのは、目標の形へ寄せるときに
**どう割ったか・なぜそう割ったか**だけ。

**WIP 行とコミット詳細の移設は 1 本にまとめ（#36）、ファイル一覧は別の PR に割った。**

まとめた側の理由。コミット詳細は M1 ではグラフペインの中で `Enter` により下部へ展開して
いたが、目標の形では右ペインに出す。移すと右ペインが「WIP かコミットか」で中身を変える
ことになるので、WIP 行が無いままでは**コミットを選んだときに詳細を出す先が無い**。逆に
WIP 行だけ先に入れると、WIP を選んでいないあいだ右ペインが Working tree のままになる。
どちらも片方だけでは成り立たない。

割った側の理由。ファイル一覧は `commit_files` という**新しい読み取り**（02）と、
`AppState::wanted_diff` が worktree の選択以外からも対象を決められるようにする拡張が
要る。まとめた側は置き場所を移すだけで読み取りを 1 つも足していない。

**一覧と `Enter` の行き先は同じ PR にする。** 一覧だけでは `Enter` の行き先が無く、
diff だけでは選ぶ経路が無いので、片方では画面から触れるものが増えない（まとめた側と
同じ形）。

commit（#34）にはこのどちらも入れなかった。`Modal::CommitMessage` はワーキングツリーの
staged を対象にするだけで、左のグラフの行にも右ペインの出し分けにも触らないため。

**狭い端末の分岐は 5 本に割った**（2026-10-04 にユーザーと決めた。`docs/plan.md` の
「端末幅 < 100 のレイアウト（1/5）〜（5/5）」）。1 本目は「右列を隠して `focus` のペインだけを
全画面で描く」だけで、**読み取りを 1 つも足さずに、80 桁の端末で右列のペインが全幅で
読めるようになる**（下の「狭い端末」）。残りは狭い幅での畳み方で、どれも「何をどの幅で
落とすか」の話。全画面切替とは別の関心事なので、1 本にすると差分が `ui` のほぼ全部に
またがる。**隠すのと全画面切替は 1 本のまま** —— 隠すほうだけを入れると、80 桁の端末から
右列のペインへ届く手段が無くなる。

畳み方は最初 1 本（2/2）にしていたが、着手前に中身を数えて 4 本に割り直した。

- **右列の幅（2/5）** —— 折り返しが 1 セルはみ出す件の余白と、1/5 で崩れた右列の前提の
  決め直し（Stash の件数、空の PR 一覧の `N`、`SUMMARY_BUDGET`）と `Enter:右へ` の文言を
  **同じ 1 本にする**。割った時点では余白を `pane_block` に足すつもりで、そうすると右列の
  内側が 38 → 37 セルに減り、数え直しの答えが変わるのが理由だった。**実装では余白を
  `ui::wrapped` へ移した**（`/simplify` の altitude を受けて 2026-10-04 にユーザーと決めた。
  下の「モーダル」）ので、右列の内側は 38 セルのまま。余白を足しても落ちるテストは
  無かった（実測 2026-10-04）ので、下の `modal_text` を先に置く必要は無い
- **見える行だけ組む（3/5）** —— `render_rows` と `NoticeLog` の中身の打ち切り。Worktree の
  パスを左で切る `…/` と、PRs の集計の上限を幅から導くのもここ（どちらも行ビルダが窓の
  幅を受け取る形に乗るので、割ると片方が宙に浮く。2/5 から移した）
- **モーダルのキーの案内（4/5）** —— 59 桁で `[Esc]` が消える件（割った時点では「52 桁」と
  書いていたが、実測すると 59 桁だった。2026-10-04）と、モーダルを読むテストを
  枠線の字から外す `modal_text`。**案内はキーの区切りで折り返す形にした**（下の
  「モーダルのキーの案内」）。そのおかげで 01 の「`Repick` に `r` を出せない理由」の
  2 つ目が消えた
- **ヘッダの落とす順序（5/5）** —— 選んでもらう点（譲る順序・`[gh: …]` の短い形・領域を
  割るか）がいちばん多く、他のどれもこれに依らないので最後に置いた。**順序と領域は
  1 本にした** —— 順序だけを決めてもスピナーに重ねて描くままだと、境目の幅でジョブが
  出入りするたびに落とす段が変わる（下の「ヘッダ › 幅が足りないとき」）

**待っているタスクの行き先も割り方で決まる。** 「既定リモートが GitHub でないときの
PRs ペインの文言」は右列の内側の幅を待っていたので 2/5 のあと（済み。下の「PRs ペイン」）、
「`Repick` に `r`」は案内の畳み方を待っているので 4/5 のあと。

### 狭い端末

**幅 100 未満では本文を割らず、`focus` のペインだけを本文いっぱいに描く**
（`ui::SPLIT_MIN_WIDTH`）。60/40 で割ると 80 桁の右列は 32 桁（枠の内側 30 セル）しか無く、
PR の行や右上のタブの見出しが切れていた。割ったときに右列がいちばん狭くなるのは
幅 100 で、40 桁（内側 38 セル）。

- **巡回の候補は幅で変えない。** `Tab` / `Shift+Tab` は同じ `focus_candidates` を回し、
  移った先がそのまま全画面になる。**閾値は `ui` だけが持つ** —— core は端末の幅を
  知らず、`Tab` の動きも変わらないので、`Msg` を足さずに済む
- **描くペインは `focus` で決まる**（Graph / Diff / Branches / Stash / PRs / Working tree /
  コミット詳細のどれでも）。Working tree とコミット詳細のどちらかはいつもどおりグラフの
  選択で決まり、候補がそれと揃っている（下の「ペインとフォーカス」）ので食い違わない
- **グラフの行数は変わらない。** グラフの高さは本文の高さだけで決まり、割るかどうかは
  幅の話なので、幅 100 をまたぐリサイズで `Msg::Layout` は流れない
- **`Esc` で Graph に戻る経路はそのまま効く**（右列のペインの `Esc` は Graph へ移る）。
  80 桁で `Enter` → コミット詳細 → `Esc` → Graph と、全画面のまま往復する
- **Graph のキーヒントは `Enter:詳細`。** もとは `Enter:右へ` で、狭い端末では右に出るのでは
  なく全画面で差し替わるので嘘になっていた。**幅で文言を変える案は採らない** —— キーの表は
  `app` にあり、幅で変えると core が端末の幅を知ることになる（上の「閾値は `ui` だけが
  持つ」）。`詳細` は WIP 行（Working tree へ）とコミット（コミット詳細へ）のどちらにも
  当てはまり、`右へ` と同じ 4 セルなので 80 桁のフッターから落ちるものは変わらない
  （2026-10-04 にユーザーと決めた）

**まだ無いペインのぶんを空枠で確保しない。** 右列を上下に割った時点（#40）では
`Stash` と `PRs` のぶんを取らず、タブの見出しも出さなかった。実装済みが 1 つしか
ないのにタブに見せると、押しても切り替わらない見出しが並ぶ（巡回に未実装のペインを
入れないのと同じ理由）。**タブにしたのは 2 枚目（`PRs`）が入ったとき**で、`Stash` は
そのペインが入ったとき（一覧と diff の PR）に 3 枚目として足した（下の「右上のタブ」）。

## ペインとフォーカス

`Pane` の定義は 01（`app`）にある。フォーカスは状態なので core が持ち、`ui` は描画するだけ。

- `Tab` / `Shift+Tab` で巡回。**巡回に入れるのは、実装済みで、かついま画面に出せる
  ペインだけ。** 狭い端末（上の「狭い端末」）では 1 度に 1 枚しか出ないが、候補はどれも
  移った時点で全画面に出るので同じ規則で回る。 順序は `Pane` の宣言順に従う。未実装のペインに移れると、キーを受け取る
  先が無い画面に入り込む。ペインを実装したら候補に足す
- **`1`〜`5` で画面の場所へ直接移る**（2026-10-06 にユーザーと決めた）。番号は場所に
  付ける —— `1` Graph、`2` Branches、`3` Stash、`4` PRs、`5` 右下。**`5` の相手は
  グラフの選択で決まる**（WIP 行なら Working tree、コミットならコミット詳細。
  `GraphSelection::right_pane()` の 1 つ）。ペインは 7 つあるが、右下の 2 つは同じ場所に
  出し分けるもので同時には出ないので、場所の数の 5 で足りる。**`Diff` には番号を
  付けない** —— 対象が無いと候補から外れる（下の条件）ので、番号を付けると断られる
  場面が増える。入るのはこれまでどおり `Enter` で、Diff で `1` を押せば Graph に戻る。
  並びは `Tab` の巡回順（`Pane` の宣言順）と同じ
  - **候補に入っていないペインの番号は、通知で断ってフォーカスを動かさない。**
    黙って何も起きないと、キーが効いていないのか対象が悪いのか判らない（下の
    「Diff ペイン」の `Enter` と同じ方針）。番号の付いたペインで候補から落ちうるのは
    `config.github.enabled = false` のときの `Prs` だけなので、文言は `A` / `r` と同じ
    `GithubBlock::AccountDisabled` の 1 本を使う
  - **いま居るペインの番号は何もしない**（`Tab` で一周したのと同じ）
  - **共通キーなので、`Tab` と同じくペインの `match` より先に見る**（01 の「キー入力」）。
    どのペインも数字をキーに使っていないので、食い合うものは無い。モーダル表示中は
    ほかのキーと同じくモーダルが受ける（`CommitMessage` では入力文字になる）
- **候補はグラフの選択で変わる**（01 の `AppState::focus_candidates`）。WIP 行を
  選んでいるあいだは `Graph` / `Branches` / `Stash` / `Prs` / `Worktree` / `Diff`、
  コミットを選んでいるあいだは `Graph` / `Branches` / `Stash` / `Prs` / `CommitDetail` /
  `Diff`。**`Branches` と `Stash` と `Prs` はどちらにも入る**（左の選択で中身が変わらない
  ペインなので、常に画面に出ている）。**`Prs` が落ちるのは `config.github.enabled = false` のときだけ**
  —— `AccountState` では変えない（下の「右上のタブ」）。
  **`Diff` はどちらの一覧にも並ぶが、出る diff は違う**
  （ワーキングツリーのファイルか、コミットのファイルか。Stash ペインの `Enter` で来た
  ときはその stash）。決めるのは
  `AppState::wanted_diff()` の 1 つ（01）。**ただし WIP 行の側は、カーソルが差分で
  表せる行にあるときだけ候補に入れる**（stash の diff を出しているあいだは除く）——
  入れたままだと `Tab` で**グラフが空の Diff に
  差し替わり**、「実装済みで、かついま画面に出ているペインだけ」を `Diff` だけが破る。
  見るのは区画ではなく行なので、conflicted と変更済みが並ぶと `j` / `k` で候補が増減する。
  コミット側を絞らない理由は 01 の「Pane と Modal」にある。
  選択と右ペインの対応そのものは
  `GraphSelection::right_pane()` の 1 つで、候補も `Enter` の行き先もそこを見る（01）。**候補にしないのは見た目の都合ではなく、`focus` と右ペインの
  中身が食い違う状態を表現できなくするため。** コミットを選んだまま `focus` が
  `Worktree` でいられると、`s` / `u` / `x` が**画面に出ていないファイル**を stage する。
  各キーにガードを配ると、キーを足すたびに書き足す必要があり、書き忘れが静かに通る
- 候補から外れるペインに `focus` が残らないよう座り直す。**引き金はグラフのカーソルが
  WIP 行を出入りしたときだけではない** —— ワーキングツリーの行を移って `Diff` が
  出入りするときもあるので、`update` の出口で毎回診る（01）。**座り直す先は `Graph`。**
  どちらの選択でも候補に残るのは `Graph` と右列の上（`Branches` / `Stash` / `Prs`）で
  （`Diff` は WIP 側で落ちることがある）、右列の上は「グラフの行を選び直したら一覧に
  飛ぶ」という説明の付かない動きになる。
  **座り直しはユーザーが選んでいない移動なので、いま見ている左の領域に戻す**
- **フォーカスのあるペインは枠を強調する。** 巡回できるペインが 2 つ以上あるのに
  どちらが受けるか判らないと、`s` や `x` が別のペインに飛んだように見える。
  **強め方は線の形と色の 2 本立て** —— 枠を太線（`┏━┓`、`BorderType::Thick`）にし、
  枠と見出しを `theme::focused()`（シアン + 太字）で描く。ほかのペインは細線のまま。
  - **形を変えるのは、修飾だけでは効かない端末があるから。** 以前は `BOLD` を足す
    だけで、太字を描かない端末では差が出ず、ユーザーから「判りづらい。bold に
    するだけじゃ足りない」と指摘が出た（2026-09-09）。線の字が違えば、色も修飾も
    出ない端末で区別が付く
  - **色は ANSI の名前付き色（パレット 0〜15）に限る。** crossterm は `Color::Cyan` を
    `ESC[38;5;6m` で送るので、実際の RGB は端末のカラースキームが決め、light / dark を
    切り替えれば追随する。`#rrggbb` で書くと端末のテーマから外れる
  - **枠の内側の大きさは強調の有無で変わらない**（太線も 1 セル）ので、行数を測る
    ときは `focused` を偽で組んでよい
  - モーダルの枠（`modals::block`）はこの対象外で、`BOLD` のまま。モーダルは表示中
    キーを全部受けるので、どれが受けるかを見分ける必要が無い
- **左の領域に Graph と Diff のどちらを描くかは `focus` だけで決める。** `focus == Pane::Diff`
  なら Diff、それ以外は Graph。「どちらを見せているか」を別に持たない。持つと `focus` と
  食い違う状態（Diff を見せているのにキーは Graph が受ける）が表現できてしまう
- **右の領域に Working tree とコミット詳細のどちらを描くかは、グラフの選択だけで決める。**
  左と違って `focus` では決めない。右ペインは左で選んでいるものの中身なので、フォーカスが
  左にあるあいだも中身は追随する必要がある。`focus` で決めると、Graph にフォーカスした
  瞬間に右が消える
- 各ペインは `trait PaneView { fn render(&self, f, area, state: &AppState); }` を実装する。
  キー処理は `app::update` 側にあり、`ui` は `Cmd` を作らない（不変ルール 2）
- **描画に使える行数は `ui` が出す。** `app` はスクロール位置を決めるのに要るが
  （01 の「グラフの行」）、レイアウトを知っているのはここだけ。`ui::graph_rows(state)` が
  描画と同じ関数からペインの高さを出し、`Msg::Layout` に載せて渡す。ランタイムが
  描画の直前に `viewport` と比べて、違うときだけ流す（01 の「ランタイム」）。
  引数は端末サイズと「詳細を出すか」の 2 つだけにする。`&AppState` を丸ごと受けると
  詳細の中身を見る余地が残り、詳細が届いた瞬間に行数が変わってグラフが跳ねる

## Graph ペイン

- 1 行は `短縮 Oid  ラベル  summary`。左のレーン罫線は `GraphRow.cells` から描く。
  1 マスの文字は `(Cell::vertical, Cell::horizontal)` の組から決まる（対応表は 06）。
  色は縦成分の `ColorId` を palette に写したもの。縦成分が無く横線だけが通るマスは
  横成分の色を使う。コミット本体のマスは常に縦の色。ASCII フォールバックの置換表も
  ここに持つ（06 の「ASCII フォールバック」）
- レーンは 1 本を 2 桁で描く。レーン間の桁は、左のセルが右へ、右のセルが左へ
  伸びているときだけ `─` で埋める（`Horizontal::goes_right` / `goes_left`）。
  その桁の色は左のセルの横線の色
- 罫線の桁数は、そのフレームで描く行のレーン数の最大に揃える。スクロールで
  桁が揺れるが、読み込み済みの全行で最大を取ると複雑な履歴で桁が育ち続ける。
  上限は設けず、はみ出す分は ratatui のクリップに任せる
- 表示するのは `scroll` から画面の高さぶんだけ。カーソル行は反転
- コミットが 1 つも無いときは、読み込み中なのか本当に空なのかを出し分ける
  （`GraphState.loaded_all` で判る）

- **先頭に WIP 行を置く。** `◇ WIP (n)` の 1 行で、`n` はワーキングツリーの変更件数
  （`WorktreeState` の合計）。ここを選ぶと右ペインが Working tree になる（上の
  「ペインとフォーカス」）
- **WIP 行は変更が無くても出す。** GitKraken は変更が無いと隠すが、隠すと
  `StatusLoaded` が届くたびに行数が増減し、カーソルが指すコミットを oid で座り直させる
  必要が出る。常に 1 行あるなら表示行は `1 + lines.len()` の定数関係になり、
  `cursor` / `scroll` / `viewport` / 追加読み込みの算術をそのまま使える
- **WIP 行にレーンの罫線を描かない。** `◇` をレーンの桁の先頭に置くだけで、HEAD の行へ
  縦線を繋がない。繋ぐには HEAD の行までの中間行に `Vertical::Through` を差し込む必要が
  あり、しかも `TOPOLOGICAL | TIME` では HEAD が 0 行目とは限らず、最初のページに入って
  いるとも限らない（06 の「ページングとの整合」）。偽のコミットを `LaneState::extend` に
  通す形は取らない。実レーンの状態が壊れる。見づらいと判った時点で M6 で決め直す
- 表示行とコミットの対応は `GraphState::row()` の 1 箇所で解く（01）。窓を切り出す
  ときもここを通し、`ui` に `- 1` を書かない。書き忘れが 1 行ずれとして静かに通り、
  反転する行と右ペインの中身が食い違う
- **カーソル行の反転は表示行の種類ごとに書かない。** WIP 行とコミット行を組んだあとに
  1 箇所で掛ける。種類を足したときに反転だけ落ちるのを防ぐ
- **`n` でカーソルの指すコミットを起点にブランチを作る**（`Modal::Input`）。
  起点は表示行から決まる — コミット行なら**その Oid**、WIP 行なら `None`（= HEAD）。
  **Oid を渡すのは、その行に何のラベルが乗っていても同じ結果になるから。** タグを
  起点にしたいときはそのタグのラベルが乗った行を選ぶ（`switch --create <名前> <タグ>`
  と `<Oid>` は同じコミットを指す）。**タグ一覧のペインは無い** — タグはグラフ行の
  ラベルとしてしか出さないので、起点に選ぶ経路もグラフに置く
- **作成後はそのブランチに切り替わる**（`switch --create`）。Branches ペインの `n` と
  同じ挙動にする。「作るだけ」と「作って移る」を同じキーの起点違いで分けると、
  どちらが起きたかがキーから読めない
- **`y` でカーソルの指すコミットを cherry-pick する**（確認モーダルを挟む。WIP 行と
  merge コミットでは断る。01 の「cherry-pick の開始（`y`）」）。**印があれば印の全部**（下）
- **`Space` でカーソルの指すコミットに印を付け外しし、`Esc` で全部外す**（01 の「複数の
  コミットの cherry-pick / revert（印）」）。印があるときの `y` / `v` は印の全部が相手。
  **印の付いた行は短縮 oid を `theme::marked()`（黄 + 太字 + 下線）で描き、枠のタイトルに
  本数を出す**（`Graph (印 3)`）。色と下線は太字を無視する端末でも残り（07 の「ペインと
  フォーカス」で `BOLD` だけでは足りないと言われた）、本数は画面外の印も数える。**行の
  桁は動かさない** —— 印の桁を足すと、印の有無で summary の桁がずれる。カーソル行の
  反転（`theme::selected()`）は行全体に掛けるので、印の行にカーソルが乗っても両方が見える
- **`v` でカーソルの指すコミットを revert する**（確認モーダルを挟む。WIP 行では断る。
  **merge コミットでは先に `MainlinePicker` で残す側の親を選ばせる**。01 の「revert の開始
  （`v`）」）。`y` と同じく印があれば印の全部
- **コミットの詳細はこのペインに出さない。** 右ペインに出す（下の「CommitDetail ペイン」）。
  M1 では `Enter` でペインの下部に展開していたが、そのぶんグラフの高さが `expanded` で
  変わり、`ui::graph_rows` と `Msg::Layout` が「詳細を出すか」を運ぶ必要があった。
  差し替えではなく分割だったのが原因で、右へ移すとその引数ごと消える

## Branches ペイン

```
│ Branches (3)                      │
│ * main            ↑1              │
│   feat/x          ↓2              │
│   release/1.0                     │
```

- **右列の上に置く**（上の「レイアウト」）。下の Working tree / コミット詳細と違い、
  **左の選択では入れ替わらない**
- **高さは「必要なぶん、ただし右列の半分まで」。** 上限が無いとブランチの多い
  リポジトリで下のペインが潰れ、下限を切らないのは 3 本のリポジトリで空行を
  抱えないため。**コミット詳細のファイル一覧と同じ規則なので、同じ関数を使う**
  （`ui::capped_rows`）。規則を写すと、片方だけ上限を変えたときに気付けない
- 1 行は `<印> <名前>  <ahead/behind>`。印は HEAD のブランチだけ `*`（`git branch` と
  同じ字）。**HEAD が detached / unborn のときはどの行にも印が付かない**（02 の
  「ブランチ一覧」）
- **ahead / behind は 0 のほうを出さない。** upstream に追いついているブランチで
  `↑0 ↓0` を出すと、桁が埋まるだけで読む情報が無い。**upstream が無いブランチと
  同じ見た目になる**が、そこを区別するのは push の `-u` 提案（M3）で、一覧では
  区別しない
- **記号は `config.graph.ascii` に従う**（`↑` `↓` / `^` `v`）。キーは `[graph]` の下に
  あるが、既定は locale から決まる（08）ので、意味は「この端末が非 ASCII の記号を
  出せるか」。グラフの罫線だけに効かせると、同じ端末で矢印だけが化ける
- 枠のタイトルは `Branches (n)`。**件数を出すのは一覧が 1 本以上あるときだけ**で、
  空・読み込み中・失敗のときは `Branches` だけにする。`(0)` を出すと、ブランチが
  1 本も無いリポジトリと読み込み中が同じ見た目になる（本文で出し分けているのと同じ
  理由）。カーソル行は反転
- **ahead / behind は名前のうしろに続けて置く**（桁を揃えない）。揃えるには一覧の
  最長の名前を数えることになり、窓の外の行まで組む必要が出る（07 の「見えない行の
  組み立て」と逆を向く）
- **空・読み込み中・失敗を出し分ける。** コミットが 1 つも無いリポジトリには
  ブランチが 1 本も無いので、空は正常な状態（`git init` の直後）。「読み込み中…」と
  同じ見た目にしない。失敗は状態から見る（`BranchState::has_failed`。消去法で
  導かない。01 の「失敗の記憶」）
- `j` / `k` で移動、`Esc` で Graph に戻る。**`Tab` でしか入れないペインにも出口を
  用意する**（Worktree ペインと同じ理由。出口がペインごとに違うと探すことになる）
- **`Enter` で切替**（`GitOp::Switch` = `switch <名前>`）。フォーカスは Branches に
  残す。続けて別のブランチを選べるようにするため。**押せるかを手前で判定しない**
  （不変ルール 4）。HEAD のブランチは `Already on '<名前>'` で成功し、ワークツリーの
  変更が衝突すれば git が断る。手前で弾くと同じ判定が mewgit と git の 2 箇所に載り、
  しかも mewgit 側は**起動時ではなく最後に読んだ一覧**でしか判定できない（別の端末で
  切り替えられていれば `is_head` は古い）
- **HEAD のブランチへの `Enter` は無料ではない。** `git switch <いま居るブランチ>` でも
  **post-checkout hook は走り**（git-lfs の smudge など。git 2.55 で確認）、成功なので
  `Reload::Refs` の読み直し 3 本も出る。カーソルの既定位置が HEAD の行なので、
  誤爆しやすい位置でもある。**それでも手前で弾かない**のは上の理由（古い `is_head` で
  「切り替えなくてよい」と決めると、実際には別のブランチに居るときに何も起きない）
- **断られた理由は 1 行だけステータスバーに出る。** `ExecError` の argv と git の出力は
  `Notice.detail` に入り（不変ルール 4）、ステータスバーは git の出力から選んだ理由の
  1 行を要約行に描く（`Your local changes to the following files would be overwritten
  by checkout:`、`the branch 'x' is not fully merged`。選び方は 01 の「失敗の案内文」）。
  **その次の行は `L` の履歴で読む**（下の「NoticeLog モーダル」）—— 上書きされる
  ファイルの名前と、未マージのときの `-D` のヒント（`hint:` なので要約に選ばれない）
- **`d` が `--delete`、`D` が `--force`。** どちらも `Modal::Confirm` を通す
  （不変ルール 5）。**未マージかも、HEAD のブランチかも手前で判定しない** —
  `--delete` は git が `the branch 'x' is not fully merged` で断って `-D` のヒントまで
  出し、HEAD のブランチは `cannot delete branch 'x' used by worktree at ...` で断る
  （どちらも git 2.55 で確認）。**断りの文は要約行に出て、ヒントは `L` の履歴で読む**（上の
  「断られた理由は 1 行だけステータスバーに出る」）
- **確認モーダルの本文は `d` と `D` で変える。** 同じ文言だと、どちらのキーで開いた
  確認なのかが画面から判らない（ハンクとファイルの discard を分けたのと同じ理由）
- **`n` で作成、`r` でリネーム**（どちらも `Modal::Input`。01 の「1 行入力」）。
  `n` の起点は HEAD（`start: None`）。**このペインは起点の情報を持たない** —
  カーソル行のブランチを起点にすると、一覧を眺めているだけのつもりで別のブランチから
  生やすことになる。起点を選んで作るのは Graph ペインの `n`（上）
- **`r` はカーソル行の名前を初期値に入れる。** 名前を少し直す操作なので空から
  打ち直させない。`n` は空で開く
- **どちらも `Modal::Confirm` を通さない。** 不変ルール 5 が確認を求めるのは破壊的な
  操作で、作成は何も壊さず、リネームは `branch --move` が既存の名前と衝突すれば
  git が断る（`fatal: a branch named 'x' already exists`。git 2.55 で確認）。
  **`--force` を付けないだけでは足りない** — `to` の前に `--` を置かないと、
  `-` で始まる入力が git 側のオプションとして拾われ、`--force` を打った人は
  **HEAD を強制改名して元のブランチを失う**（03 の「argv への変換」に実文言がある）
- 一覧が空（読み込み中・失敗・`git init` の直後）のあいだ、`Enter` / `d` / `D` / `r` は
  何もしない。**カーソル行が描かれていないので、通知を出す相手もいない**
  （「黙って何も起きない」を避けるのは、行を選んだうえで断られたときの話）。
  **`n` だけは空でも開く** — 作成はカーソル行を要らず、`git init` の直後
  （ブランチが 1 本も無い）はまさに作りたい状態。`switch --create` は unborn HEAD でも
  通り、`HEAD` を新しい名前に向け替える（git 2.55 で確認）
- **スクロールは Worktree ペインと同じ**（状態を持たず毎フレーム導く。`ui::render_rows`）

## 右上のタブ

右列の上は `Branches` / `Stash` / `Prs` の 3 枚を差し替えで使う。枠のタイトルに全部を
並べ、**いま出ているものを強調する**。

```
┌ Branches (3) | Stash | PRs ──────────┐
 ^^^^^^^^^^^^^^ ^^^^^^^ ^^^^^
```

`^` の 1 つ目の塊が反転、残りが `DIM`（どれも前後の空白を含む）。

- **出ているほうは前後 1 空白ごと反転（`theme::current_tab()`）、出ていないほうは
  `theme::muted()`。** 以前は出ていないほうを `DIM` にするだけで、`DIM` を無視する
  端末では 2 枚が同じに見えた（上の「ペインとフォーカス」の枠と同じ指摘）。反転は
  どの端末でも出る。空白ごと反転するのは、語の端がそのまま枠線に接すると塊に
  見えないから
- **強調は `focus` ではなく `right_tab` に付く。** フォーカスが Graph にあっても、
  右上でどちらを出しているかは見出しで判る必要がある。フォーカスがこのペインに
  あるかどうかは枠のほう（太線 + 色）が示すので、2 つは別のことを答える
- **タブは常に 2 枚以上**（`Stash` は GitHub を切っても残る）ので、どれか 1 枚を
  必ず強調する。`Stash` が入る前は、GitHub を切るとタブが 1 枚になり強調を外していた
- **`Stash` の見出しにも件数を添える**（`Stash (3)`。0 件と読み込み中は `Stash` だけ ——
  `Branches (n)` と同じ規則）。**最初は添えなかった** —— 80x24 でも右列を割っていたころは
  枠の内側が 30 セルで、`Branches (12)` / `Stash (3)` / `PRs` を前後の空白と区切りごと
  並べると 33 セルになり `PRs` が切れた。80 桁で右列を割らなくなって（上の「狭い端末」）、
  右列がいちばん狭い幅 100 でも見出しに使えるのは 38 セルになり、`Branches (1234)` /
  `Stash (123)` / `PRs` でも 37 セルで入る。**Branches と Stash は `panes::counted` の
  1 本で組む**（`(0)` を出さない規則を片方だけ直さないため）
  （2026-10-04 にユーザーと決めた）

- **どちらを描くかは `right_tab`**（01 の「PR ペイン › 右上のタブ」）。`focus` だけでは
  決めない —— 左（Graph / Diff）と違い、**チェックの結果を見ながら `j` でグラフを
  辿った瞬間に消える**。右下ペインを `focus` で決めないのと同じ理由（上の「ペインと
  フォーカス」）
- **切り替えるキーは足さない。** `Tab` の巡回が `Branches` → `Stash` → `Prs` と通るので、
  タブ専用のキーを置くと同じことをする経路が 2 本になる
- **`config.github.enabled = false` のときは `Prs` の見出しを出さない**（`Prs` が巡回
  候補から落ちるため）。**押しても切り替わらない見出しを並べない**のは、まだ無いペインの
  ぶんを空枠で取らないのと同じ（上の「まだ無いペインのぶんを空枠で確保しない」）。
  **出す見出しは巡回候補から導く**（`panes::right_tabs`）ので、ここで数え直さない

## Stash ペイン

```
┌ Branches (3) | Stash | PRs ──────────┐
│ stash@{0}  On main: wip              │
│ stash@{1}  WIP on main: 6dd895c init │
```

- **右上のタブの 2 枚目**（上の「右上のタブ」）。Branches と同じく左の選択では入れ替わらず、
  高さの規則・カーソル行の反転・スクロールも同じもの（`panes::TopPane`）
- 1 行は `stash@{n}  <メッセージ>`。**`stash@{n}` を先に置く** —— 右列は狭く
  （上の「狭い端末」）、メッセージは右で切れる。番号が残れば、端末で `git stash show stash@{n}` を
  打つときの手掛かりになる。メッセージは reflog の本文そのまま（02 の「stash 一覧」）
- **空・読み込み中・失敗を出し分ける**（「stash はありません」「読み込み中…」
  「stash を読み込めませんでした」）。stash が 1 つも無いのは正常な状態
- `j` / `k` で移動、`Esc` で Graph に戻る（Branches と同じ出口）
- **`Enter` で左に stash の diff を出す**（下の「Diff ペイン」。01 の「Stash ペイン」）。
  `Esc` で Stash に戻る。一覧が空なら何もしない（カーソル行が描かれていない。
  Branches と同じ）
- **`z` で push、`a` / `Z` / `d` でカーソル行を apply / pop / drop**（01 の「stash の
  書き込み」）。drop だけ `Modal::Confirm` を挟み、本文に `stash@{n}` とメッセージを出す。
  `z` は Worktree と同じく一覧が空でも開く（退避する相手は作業ツリー）

## PRs ペイン

```
┌ Branches │ PRs ──────────────────────────────┐
│ *#123 OPEN   ✓3 ✗1  A1  Add adaptive layout  │
│  #121 OPEN   ✓4         Fix lane colors      │
│ *#118 DRAFT  …          Bump rust to 1.98.1  │
│ R#112 OPEN   !          Speed up the log walk│
└──────────────────────────────────────────────┘
```

- **出すのはこのリポジトリで開いている PR の一覧**（01 の「PR ペイン」）。1 行 1 件で、
  `j` / `k` で動かし、`o` でカーソル行を `gh browse` に渡す
- **`r` でカーソル行の集計と一覧を引き直す**（01 の「引き直す（`r`）」）。**画面は
  2 段階で変わる** —— 押した直後にその行の集計が `…`（まだ引いていない）に戻り、
  答えが届くと埋まる。待ちの印を「集計 0 件」と同じ見た目にしないこと（下の
  「チェックの桁は 3 つの意味を載せる」）が、ここでも効く。**手応えは `…` だけでは
  ない** —— ヘッダの右端にスピナーが出る（下の「ヘッダ」）。一覧が空のリポジトリでは
  そちらしか出ない
- 1 行は **印 1 文字**・`#<番号>`・状態（`OPEN` / `DRAFT`）・タイトル。
  **`MERGED` / `CLOSED` はこの一覧に出ない**（`state=open` だけを引く。01 の
  「現ブランチの PR」）が、**状態の語は 4 つとも残す** —— `PullRequest` は
  `PrStatus` を運んでおり、出ない腕のために文言を削ると `Modal::PrCreate` や
  PR チェックアウトが同じ写像をもう 1 本書くことになる
- **印は `*`（自分が作った PR）と `R`（自分にレビューが依頼されている PR）。**
  それ以外は空白 1 文字。**`*` と `R` は衝突しない** —— 自分の PR のレビューを
  自分に依頼することはできない
- **`R` が見るのは `requested_reviewers` だけ。** **チーム宛ての依頼
  （`requested_teams`）には印が付かない** —— チームの一員かどうかを答えるには
  `/orgs/{org}/teams/{team}/memberships/{login}` をチームの数だけ叩くことになり、
  一覧 1 回の往復が読めなくなる。**受け入れた穴**で、塞ぐなら所属の取得ごと
  別のタスクにする
- **状態をタイトルより前に置く。** 右列は端末幅の 40% しかなく、ratatui は行の右端で
  切るので、末尾に置くと**状態だけが黙って消える**（実測: 幅 100 の右列 38 桁で
  `MERGED` が出なかった）。**印を先頭に置くのも同じ理由** —— 行の左端は切られない
- **カーソル行は反転**（Branches / Worktree と同じ）。**行頭に `>` を足さない** ——
  反転と二重になるうえ、印の桁と並んで「どちらが印か」が読めなくなる
- **並びは API が返した順**（`sort=updated&direction=desc`）。`ui` で並べ替えない ——
  並べ替えると、カーソルを番号で座り直す規則（01）が `app` と `ui` で 2 本になる
- **空・読み込み中・失敗を出し分ける。** Branches ペインと同じ形だが、**腕はもっと
  多い**（アカウントが決まっていない / degraded / まだ引いていない / 引いたが
  open な PR が 1 件も無い / 引けなかった）。**消去法で導かず、`PrState.list` の
  `Fetch` と `AccountState` から出す**（01 の「失敗の記憶」と同じ理由）
- **「開いている PR はありません（N）」と `N` を添える。ただし `N` が効くときだけ。**
  行き止まりを作らないため（#63）。**`N` が効くのはこのペインにフォーカスがあり、モーダルが
  出ていないとき**で、幅 100 以上ではフォーカスが Graph のまま右上にこの文言が見える。
  そこで添えると押しても何も起きない案内になる（`.claude/rules/rust-coding.md` の
  「案内にキーを書いたら、その案内が出ている画面でそのキーが効くかを数える」）。**効くかは
  `keys::is_live` に聞く** —— `ui` が `focus` を見て決めると、振り分けの規則（モーダル
  表示中はキーを全部モーダルが受ける）の写しが 2 本になる（`/simplify` の altitude が拾った）。
  書き方は degraded の `GitHub: …（A）` と同じ「括弧にキー」で、31 セル。`（N で作成）` も
  右列がいちばん狭い幅 100 の内側 38 セルにちょうど入るが、余りが 0 で右列が 1 セルでも
  減る変更が入ると末尾が切れるので `（N）` にした。
  **最初は添えなかった**（決めたときの枠の内側は 80x24 で 30 セル）。そのあいだも
  行き止まりではなかった —— このペインにフォーカスがあるあいだフッターの 2 行目が
  `N:PR 作成` を出しており、`N` が効くのはまさにそのとき（2026-10-04 にユーザーと決めた）
- **既定リモートから GitHub のリポジトリを特定できなければ「GitHub のリポジトリを特定
  できません」と出す。** `TargetState::Unavailable` ではアカウントの解決を頼まない（01）ので
  `AccountState::Resolving` のまま二度と動かず、「読み込み中…」を出すと**永久に待たせる**。
  待てば変わるかは `AppState::github_block` に聞く（`TargetUnavailable` か
  `AccountResolving` か。`TargetState` を自分で読み直さない —— 01 の「引き直す（`r`）」）。
  **`A` の通知の文言（「既定リモートから…」、52 セル）とは分ける** —— 右列がいちばん狭い
  幅 100 の内側 38 セルに入らないので、結論だけを残した 35 セル（2026-10-05 にユーザーと
  決めた。2 行に折って通知と字を揃える案は、このペインの文言が 1 行である前提を崩すので
  採らなかった）。**キーを添えない** —— `A` を押しても同じ事実が通知に出るだけで、
  直す操作を mewgit は持っていない。**`Disabled` のようにタブごと消す形は採らない** ——
  `Unavailable` も起動中は変わらないが、消すと「なぜ PRs が無いのか」が画面から消える
  （`Disabled` は自分で切った設定なので、言い返さなくてよい側）
- **`ui::LOADING` を使う。** 文言を自分で組むと、既にある「読み込み中…」の見張りが
  この産出元を拾えない（`.claude/rules/testing.md` の「共有した見張りは新しい産出元を自分では
  拾わない」）
- `Esc` で Graph に戻る（Branches ペインと同じ。`Tab` でしか入れないペインにも出口を
  置く）
- **スクロールは `ui::render_rows`**（状態を持たず毎フレーム導く）。open な PR が
  数十件あるリポジトリでは枠に収まらない
- **チェックの桁は 3 つの意味を載せる。** 集計が**居ない**のは「まだ引いていない」
  （`app::PrDetailEntry`）で待ちの印、`Err` は「引けなかった」で `!`、`Ok` は数えた
  結果。**どれも同じ見た目にしない** —— 引けなかった行を「チェック 0 件」と同じに
  見せると、CI の無い PR と CI を読めなかった PR が区別できない
- **記号は `ui::pick_charset` を通す**（`config.graph.ascii`。Branches ペインの
  `↑` `↓` と同じ理由で、同じ端末で一部の記号だけが化けるのを避ける）。
  **記号は `CheckState` の腕ごとに 1 つ。畳まない** —— 畳むと `Skipped` と
  `Neutral` が成功か失敗のどちらかに見え、**どちらも嘘**（対応は下の表）

  | 意味 | UTF-8 | ASCII |
  |---|---|---|
  | `Success` | `✓` | `+` |
  | `Failure` | `✗` | `x` |
  | `Pending` | `○` | `o` |
  | `Skipped` | `⊘` | `-` |
  | `Neutral` | `·` | `~` |
  | まだ引いていない | `…` | `.` |
  | 引けなかった | `!` | `!` |

- **0 のものは出さない**（Branches ペインの `↑` `↓` と同じ）。1 件も無ければ空文字
  になり、**どの行にも出すものが無ければ桁ごと消える** —— **桁を先に確保しない**
  （空の列を置くと、意味の無い余白がタイトルの桁を食う）
- **レビューは英字で出す**（`A2 C1`）。**`✓` / `✗` を使い回さない** —— あれは
  チェックの語彙で、同じ記号にすると「CI が通った」と「人が承認した」が同じ見た目に
  なる。**`commented` は出さない** —— 承認でも変更要求でもないコメントは、出しても
  次に何をするかが変わらない（値は `ReviewSummary` が持っているので、出す場所が
  できたときに数え直さずに済む）
- **チェックとレビューは 1 本の桁にまとめる。** 別々の桁にすると区切りの 2 セルが
  もう 1 組要り、それだけでタイトルが消える
- **桁は出す行から幅を導いて揃える**（状態の桁と同じ。行ごとに中身の幅が違うので、
  揃えないとタイトルの開始位置がずれる）
- **桁には上限がある**（`panes::prs::summary_budget`）。**この守りは上の「末尾に
  置くと黙って消える」がそのまま自分に返ったもの** —— 集計を伸ばし放題にすると、
  今度は**タイトルが 1 文字も出ない行ができる**。**上限は枠の内側の幅から導く**
  （2026-10-04 にユーザーと決めた）—— 内側の幅から印・`#番号`・状態・区切り 2 つを
  引き、タイトルに `TITLE_MIN`（6 セル）を残した残り。`#番号` と状態の桁は一覧の最大から
  出す（どちらも行ごとに揃えるので）。右列がいちばん狭い幅 100（内側 38 セル）で番号が
  2 桁・状態の桁が 5（`DRAFT` がある）なら 17 で（`OPEN` だけなら 18）、チェック 5 種の `✓12 ✗3 ○2 ⊘5 ·1`（15 セル）に `+` を足しても入る。
  **6 は定数にしていたころの値をそのまま引き継いだ** —— 17 を決めたとき、いちばん
  広い行でタイトルに残ったのが 6 セルだった（実測 2026-10-04）。それまでは「幅 100 で
  測った定数」で、10（80x24 の右列 30 セル）→ 17 と 2 回数え直しており、右列が広い
  端末でも `+` で畳まれていた。**いちばん前の 1 つは上限を越えても出す** —— 全画面の
  狭い端末で上限が数セルに縮んでも、成功か失敗のどちらかは読める（タイトルが
  そのぶん削られる）。しかも**桁の幅は一覧の最大から決まる**ので、
  広い行が 1 つあると狭い行のタイトルまで巻き添えになる。
  **超えたぶんは後ろから落とし、`+` を付ける** —— 落としたことを言わずに消すと
  「それ以上は無い」と読める。落とす順は並びの後ろから（前に置いてあるほど
  「次に何をするか」が変わる）
- **引けなかった理由は行に出ない。** 枠の内側に入らないので、出せるのは `!` だけ
  —— **受け入れた穴**。扇形ごと打ち切られたときは通知が出るが、**理由は
  `Notice.detail`**（要約行に混ぜると 1 行目の予算を超える。01）なので、**理由は
  `L` の履歴で読む**（下の「NoticeLog モーダル」）。
  **それでも行き止まりにはならない** —— 引けなかった記憶は次に一覧が届いたときに
  落ちるので、`f` で引き直せる（01 の「PR ペイン › 集計」）

## Worktree ペイン

```
│ Working tree (3)                  │
│  Staged                           │
│   M src/main.rs                   │
│  Unstaged                         │
│   M src/graph.rs                  │
│  Untracked                        │
│   ? notes.md                      │
```

- 区画の見出しと、その中のファイルを 1 行ずつ並べる。**空の区画は見出しごと出さない。**
  カーソルが飛ばす区画を描いても、選べない行が増えるだけ
- 1 行は `<種別 1 文字> <パス>`。rename は `<旧パス> -> <新パス>`。種別は
  `M A D R C T ?` と、conflicted の `U`
- カーソル行は反転。カーソルの位置（区画と添字）は `WorktreeState` が持つ（01）
- **パスが枠に入らないときは左を切って `…/` にする**（`ui::file_row` が枠の内側の幅を
  受ける。2026-10-04 にユーザーと決めた）。右で切るとファイル名が消え、深いディレクトリの
  変更がどれも同じ行に見える。**切る単位は `/` の区切り** —— 先頭の成分から落とし、
  `…/` + 残りが入るいちばん長い形にする。**ファイル名だけでも入らないときは**、書記素
  単位で左を落として `…` + 末尾にする（幅は `ellipsize` と同じく書記素で測る）。
  rename（`<旧> -> <新>`）も 1 本の文字列として左から切るので、狭いと旧い名前から
  消える —— **受け入れた穴**。種別の `R` で rename であることは読める
- 見出しの `Working tree (n)` の `n` は全区画の合計
- **スクロールはグラフと違い、状態を持たずに毎フレーム導く**（カーソルが窓に入るまで
  下へずらすだけ）。そのぶん「下端から上へ戻るときにカーソルが最下行に貼り付く」癖が
  残る。グラフはこれを避けるために `scroll` を状態に持ち `Msg::Layout` で `viewport` を
  運んでいる（01）。**右ペインには入れない**（2026-10-04 にユーザーと決めた）——
  このペインの高さは右上のタブの行数で動く（ブランチ一覧が届くと縮む）ので、`viewport` を
  運ぶと `Msg::Layout` が一覧の到着ごとに流れ、`ui::graph_rows` の「引数は端末サイズと
  詳細を出すかだけ」（上の「レイアウト」）にも例外が要る。貼り付く癖は劣るが、行を
  見失うわけではない
- `Esc` で Graph に戻る。**グラフの `Enter` で入ってくる先なので出口を用意する。**
  無いと、`Enter` の行き先がコミット詳細か Working tree かで出口が変わる
  （片方は `Esc`、もう片方は `Tab` を探す）
- キーは `s`（stage）/ `u`（unstage）/ `x`（discard）。`x` は必ず `Modal::Confirm` を
  通す（不変ルール 5）。何が起きるかは区画で変わるので、**確認の本文も区画ごとに
  変える**（untracked は「ファイルを削除します」、tracked は「HEAD の状態に戻します」）
- **`z` で全体、`Z` でカーソルの 1 ファイルを stash**（01 の「stash の書き込み」）。
  フッターと `?` の一覧では **`z/Z:stash 全体/1 ファイル` の 1 行に束ねる** —— 分けると
  `?` の一覧が 80x24 に収まらない（下の「Help モーダル」）

## CommitDetail ペイン

グラフでコミットを選んでいるあいだ、**右の領域に Working tree と差し替えで描く**
（上の「ペインとフォーカス」）。WIP 行を選べば Working tree に戻る。

```
│ Commit a1b2c3d                    │
│ commit a1b2c3d4e5f6...            │
│ Author: Name <mail>  2026-09-06 …│
│ Commit: Name <mail>  2026-09-06 …│
│ Parent: d4e5f6a                   │
│                                   │
│ Add the thing                     │
│                                   │
│ Files (2)                         │
│  M src/main.rs                    │
│  A README.md                      │
```

- 枠のタイトルは `Commit <短縮 Oid>`。**対象を必ず出す。** 右が差し替わっているので、
  出さないと誰の詳細かを画面から辿れない（Diff ペインと同じ理由）
- 見出しの高さは折り返し後の行数から出し、メッセージには必ず `MIN_MESSAGE_ROWS` 行を
  残す。見出しは幅が狭いと折り返して伸びる（決めたときは 80 桁でも右列を割っていて、右ペインが
  32 桁になり `Author: 名前 <メール>  日時` が 3 行以上になった）。1 つの `Paragraph` にまとめると、
  伸びたぶんメッセージが下から押し出されて**本文が 1 行も見えなくなる**。先にメッセージの
  領域を取り、足りないときは見出しのほうを切る
- メッセージは描ける行数までしか組まない。折り返しで増えることはあっても減ることは
  ないので、見える行は落ちない。revert やマージの本文は数百行になりうる
- 出す値は `GraphState::fresh_detail()`（01）。**カーソルの指すコミットの oid と
  `detail.oid` が一致するときだけ中身を出す。** 一致しないのは、まだ届いていないか
  失敗したときなので、`JobTracker` に `LoadCommitDetail` が居れば「読み込み中…」、
  居なければ「詳細を読み込めませんでした」を出す。空のグラフの出し分けと同じ形
- 日時はコミット自身のタイムゾーンで出す（`Timestamp.offset_minutes`）。`git show` と
  同じで、見る人の環境のタイムゾーンには寄せない。整形は `ui::time`。日時のクレートは
  足していない（要るのは「秒数 + オフセット」から暦を起こすことだけで、純粋関数に
  収まる。通知の時刻も同じ関数を通る —— あちらのオフセットは `Timestamp::now` が
  libgit2 から取る）
- **このペインの高さはグラフに影響しない。** 右の領域に描くので、`ui::graph_rows` は
  端末サイズだけから決まる。M1 の下部展開ではここが `expanded` に依存していた
- **ファイル一覧はメッセージの下に置き、行の形は Worktree ペインと同じ**
  （`<種別 1 文字> <パス>`、rename は `<旧> -> <新>`）。**行の組み立ては 1 本**にする
  （`ui::file_row`）。区画の見出しを挟むかどうかはペインごとに違うが、行そのものが
  2 本あると種別の字だけが片方で古くなる。**長いパスを左で切って `…/` にするのも
  同じ関数**（上の「Worktree ペイン」）なので、こちらにも効く
- **一覧に割く高さは「必要なぶん、ただし内側の半分まで」。** メッセージは 1 行の
  summary で終わることが多く、固定で割るとその下が空くか、逆に長い本文が一覧に
  押し出される。上限を置くのは、ファイルの多いコミットで**メッセージが 1 行も
  見えなくなる**のを防ぐため（見出しに `MIN_MESSAGE_ROWS` を確保しているのと同じ理由）
- 一覧は `j` / `k` で選び、`Enter` で左を `DiffTarget::Commit` の diff に差し替える
  （`Pane::Diff` へ移る）。`Esc` は Graph に戻る。**選んでいる行は反転**させる。
  どのファイルの diff が左に出ているかが、左のタイトルと合わせて 2 箇所から辿れる
- 出す値は `GraphState::fresh_files()`（01）。詳細と同じく oid の一致で濾し、一致
  しなければ `JobTracker` に `LoadCommitFiles` が居るかで「読み込み中…」と
  「ファイル一覧を読み込めませんでした」を出し分ける。**空の一覧は「変更はありません」**
  （`--allow-empty` のコミット）。読み込み中と同じ見た目にしない
- **詳細と一覧は別々に届く。** 片方だけ来ている時点があるので、メッセージが出て
  いるのに一覧が「読み込み中…」ということが普通に起きる。1 つの `Msg` にまとめない
  理由は 01 にある

## Diff ペイン

```
│ Diff: src/main.rs                 │
│  @@ -1,4 +1,6 @@ fn main() {      │
│   fn main() {                     │
│  -    println!("old");            │
│  +    println!("new");            │
```

- **左の領域に、Graph と差し替えで描く**（上の「レイアウト」）。右のワーキングツリーは
  出したままにするので、どのファイルを見ているかが一覧の側でも判る
- 枠のタイトルは `Diff: <パス>`。rename は `<旧> -> <新>`。**対象を必ず出す。**
  左が差し替わっているので、出さないと何の diff かを画面から辿れない。**stash の diff は
  `Diff: stash@{n}`**（ファイル数に関わらず。一覧から消えていれば番号は名乗れないので
  `Diff: stash`）
- 中身はハンクの見出し（`@@ ...`）と行を順に並べる。行の先頭は ` ` / `-` / `+`。
  **ファイルの見出し（パス 1 行、弱い色）は、対象が `path` で 1 ファイルに絞られて
  いないときだけ挟む**（`panes::diff::names_file` は `target.path().is_some()`）。
  ワーキングツリーとコミットの diff は一覧で選んだ 1 件に絞ってあり、タイトルが名乗って
  いるので、挟むと同じ名前が 2 度並ぶ。**stash の diff は絞らないので、1 ファイルでも
  見出しを挟む**（タイトルは `stash@{n}` を名乗り、挟まないとどのファイルの差分かが
  画面のどこにも無い）。**「stash なら」と変種で書かない** —— `path` を持たない対象を
  足すたびにここへ足すことになる
- **stash の diff では `s` / `u` / `x` を断る**（「stash の差分は変更できません」。
  01 の「Stash ペイン」）。キーヒントは Diff ペインのまま出す（コミットの diff と同じ。
  下の「ステータスバー」—— ヒントはペイン単位）
- **折り返さない。** 長い行は右で切る。diff は桁の揃いが意味を持つので、折り返すと
  どの行がどの行に対応するのか読めなくなる
- **`content` は `Vec<u8>` なので、描くときにその場で lossy にする**（02 の
  「ハンクの持ち方」）。`\t` は **8 桁のタブストップで空白に開く**。1 個の空白に潰すと
  インデントが崩れて、上下の行の対応が読めなくなる。桁は**先頭の `-` / `+` / ` ` を
  除いた本文の先頭から**数える（記号を含めて数えると、変更行と文脈行でタブストップが
  1 桁ずれる）。`\r` は落とす。落とさないと CRLF のファイルで制御文字が画面に出る
- カーソルはハンク単位（`DiffCursor`）。`j` / `k` で次のハンクへ移る。
  `s` / `u` / `x` はカーソルの指すハンクに効く。可否の表は Worktree ペインと
  共通（01 の `update::plan`）
- **ハンク単位の `GitOp` を出すのは `status == Modified` で、バイナリでなく、
  ハンクがあるときだけ。** それ以外（Untracked / Added / Deleted / Renamed /
  Typechange）は「ハンク = ファイル全体」なので、**同じキーがファイル単位の操作に
  落ちる**。`--- /dev/null` や `rename from` / `rename to` を組み立てる領域に
  入らずに済む。落ちたことは通知に出さない（結果は「そのファイルを stage した」で、
  押した意図と一致する）
- **`x` は Unstaged のハンクだけ。** staged なハンクを捨てるには index と
  ワークツリーの両方に当てることになり、`git apply` は 1 回で片方にしか効かない
  （03）。「先に unstage してください」と断る
- **出しているハンクが書き込みより前のものなら（`AppState::diff_is_current` が偽）
  ハンク単位の `s` / `u` / `x` を断る。** そこから組んだパッチは `git apply` の
  オフセット追従で別のハンクに当たりうる（01 の「diff のキャッシュと鮮度」）。
  **断るのはハンク単位のときだけ**で、ファイル単位に落ちる操作は古いパッチを
  使わないのでそのまま通す
- **diff が出ていないあいだ（「読み込み中…」「差分を読み込めませんでした」）は
  `s` / `u` / `x` を断る。ファイル単位に落とさない。** 上の fallback は「ハンクで
  表せないファイル」のためのもので、届いていないファイルのためではない。落とすと、
  ハンク 1 つのつもりで押した `s` が**ファイル全体**を stage する。文言は鮮度の
  ときと同じ（どちらも「最新の差分を持っていない」）
- **スクロールは「カーソル行」ではなく「選んでいるハンク全体」を窓に入れる**
  （`ui::window` に見出しから本文の末尾までの範囲を渡す）。カーソル行 1 行だけを
  入れる規則にすると、ハンクの見出しがちょうど窓の下端に来て**本文が 1 行も見えない**。
  見えていないハンクに対して破壊的な操作を押すことになる。ハンクが窓より高いときは
  見出しを優先して残りを切る。Worktree ペインはカーソルの 1 行を渡すだけで、
  規則そのものは 1 つ
- **`state.diff.view` を直に描かない。** `DiffState::fresh_view(wanted)` を通す
  （01 の「diff の遅延取得」）。対象が変わってから届くまでのあいだ、別のファイルの
  diff をタイトルごと出したままにしないため
- 空のとき（バイナリ、mode だけの変更、内容の同じ rename、中身が空のファイル、
  まだ届いていない）は理由を出す。**「失敗した」と「待っている」を消去法で導かない。**
  `DiffState::has_failed` が事実として持っているほうを先に見る。
- **対象が決まらないままこのペインが出るのはコミット側だけ。** ワーキングツリーの行で
  決まらないとき（変更が無い、一覧が届いていない、conflicted）は `Diff` が巡回の候補から
  外れ、`Enter` も断られる（上の「ペインとフォーカス」）ので、ペインごと出ない。
  残るのは**ファイル一覧が決まらない形**なので、**理由は CommitDetail ペインの一覧と
  同じ文言を使う**（「読み込み中…」/「ファイル一覧を読み込めませんでした」/
  「変更はありません」。上の「CommitDetail ペイン」）。書き直すと 3 通りのどれかが落ちる
- **ハンクが 0 個の理由も一括りにしない。** バイナリ・mode だけの変更・内容の同じ
  rename・中身が空のファイルはどれもハンクが空になる（02）。`binary` と
  `FileStatus` から出し分ける。全部を「mode だけの変更」と出すと、`touch` した
  だけの空ファイルにも mode の話をすることになる
- 入るのは Working tree ペインか CommitDetail ペインで `Enter`、出るのは `Esc`。
  `Tab` の巡回にも入る。**Working tree ペインからの `Enter` は「差分で表せる行か」を
  見る** —— 表せない行では理由を通知に出して断る（`Tab` も同じ判定で候補から外す。
  上の「ペインとフォーカス」）。黙って何も起きないと、キーが効いていないのか対象が
  悪いのか判らない。**CommitDetail ペインからの `Enter` は断らない** —— コミット側は
  候補を絞らないので、ファイルが 0 件のコミット（`--allow-empty`）では対象の無いまま
  Diff に入る（01 の「Pane と Modal」が「いまの挙動のまま」と決めた形）。そのとき出す
  文言は上の「対象が決まらないまま出るのはコミット側だけ」で決めている。
  **`Esc` の戻り先はグラフの選択で決まる**
  （`GraphSelection::right_pane()`。WIP 行なら Working tree、コミットなら
  CommitDetail）。`Enter` で来た側へ戻るので、行き先と戻り先が同じ 1 つの関数から出る
- **コミットの diff では `s` / `u` / `x` を断る。** 対象はワーキングツリーの選択行だが、
  画面に出ているのはコミットの中身なので、通すと**見えていないファイル**を stage する
  （`focus` の候補で防いでいるのと同じ形の事故。上の「ペインとフォーカス」）。
  黙って無視せず理由を通知に出す

## ステータスバー

**フッターは 2 行。** 1 行目が進行中操作と直近の通知、2 行目がフォーカス中のペインで押せるキー。

```
│ 10:03:26 変更のないファイルは stage できません                                 │
│ j/k:移動 Enter:差分 s:stage u:unstage x:破棄 c:commit C:amend  ?:help q:quit   │
```

- **高さは固定 2 行。** 中身で変えると `Msg::Layout` 経由でグラフの行数が動き、**通知が
  1 件出るだけでログの読み直しが走る**（01 の「グラフの行」）。そのぶん本文は 1 行減る
  （80x24 でグラフ 20 → 19 行）
- **1 行目は進行中操作と通知だけ。** 実行中ジョブはここに出さない（出す先はヘッダの右端。下の
  「ヘッダ」）
- **進行中操作も 1 行目の先頭にバッジで出す**（`theme::in_progress()`。前後に空白 1 つ
  ずつを含めて反転）。**通知が無いときも出し続ける** —— 通知は次の入力で下ろすが、
  進行中操作は continue / abort するまで終わらない。文言は git の語を大文字で ——
  `REBASE 3/7` / `AM 1/2` / `CHERRY-PICK abc1234` / `REVERT abc1234` /
  `MERGE abc1234`。進捗が読めない rebase は `REBASE` だけ、`sequencer/` だけが残った
  pick / revert は oid を出さない（02 の「進行中操作の検出」）
  - **止まった理由（`(edit)` など）は出さない。** 以前のモックには `REBASE 3/7 (edit)` と
    書いていたが、`done` の最終行は理由を表さない（02 の実測）
  - **数は git の数えた todo の行数**で、`-x` を付けるとコミット数より大きい（02）
  - **通知の予算（71 セル）は縮めない。** バッジがいちばん長いのは `CHERRY-PICK abc1234`
    で、前後の空白と区切りを足して 22 セル。**バッジが出ているあいだの通知は 49 セルで
    `…` に切れる**（80 桁）。予算を 49 に縮めると、進行中でないとき（ほとんどの時間）の
    案内文まで痩せる（#73 の「予算の狭いほうが広いほうを痩せさせる」）。切れた全文は
    `L` の履歴で読む。バッジと時刻を前置きとして `ui::lead_line` に渡すので、溢れ方は
    通知だけのときと同じ 1 本の規則
- **2 行目はフォーカス中のペインで押せるキーだけ。** 全部を並べると 80 桁に収まらず、
  ペインを足すたびに溢れる。**押せないキーを案内しないのは、未実装のペインを `Tab` の
  巡回に入れないのと同じ理由**（上の「ペインとフォーカス」）。全部を見るのは
  `Modal::Help`
- **並びは `ペインのキー  ?:help q:quit`**（2026-09-30 にユーザーと決めた）。**`?:help` と
  `q:quit` は必ず残す。** 幅が足りないときに落とすのはペインのキーのほうで、**末尾から
  順に**落とす。落ちたキーは `?` の一覧（下の「Help モーダル」）から辿れるが、その入口と
  終了の入口が落ちるとそもそも辿れない・抜けられない。**右端に寄せない** —— ヒントの
  直後に空白 2 で置く
  （右寄せにすると、落とす判断が「どこまで入るか」ではなく「隙間がいくつ残るか」の話に
  なる）
- **高さも数える。** フッターに 2 行渡らない端末（高さ 3 以下。リサイズ中の一瞬）では、
  **落とすのは通知の行のほう** —— `Layout` に 1 行ずつ割らせると後ろのキーヒントが
  0 行になり、`q:quit` が画面から消える（80x3 で実測。`ui::split` が算術で割っている
  のはこのため）。**幅の守りだけを書くと、高さでは効かない**
- **幅が 6 に足りなければ `q:quit` 自体が切れる**（`q:qui`）。そこはもう案内の問題では
  ないので、落とす規則では扱わない（幅 5 は実用外。80 桁を前提に予算を決めている）
- **共通キー（`f` / `p` / `P` / `A` / `L` など、どのペインでも効くキー）はフッターに
  出さない**（2026-09-30 にユーザーと決めた）。出すのは `?` の一覧（下の「Help モーダル」）
  だけ。**それまでは幅が余るペインでだけ、共通キーの末尾から 1 つずつ落として出していた**
  が、ペインにキーを足すたびに共通キーが見えなくなり、辿る手段が無かった。実測（80 桁、
  `q:quit` 込み）—— `L` を足した 2026-09-26 に全部出るのは CommitDetail だけ、Graph は
  `y` / `v` を足した 2026-09-29 に `f` しか残らなかった。lazygit 0.65.1 と gitui 0.28.1 も
  同じ形 —— 最下段はいまのパネルのヒントを少しだけ出し、lazygit は `Keybindings: ?`、
  gitui は右端の `more [.]` を必ず残す（2026-09-30 に pty で撮った。どちらも最小幅で起動を
  断らず、狭いと詰めて描く）
- **`x:破棄`（6 セル）を `x:discard`（9 セル）にしない** —— Worktree のペインのキーが
  さらに 3 セル伸び、80 桁で落ちるキーが増える
- **モーダル表示中は 2 行目を空にする。** キーはモーダルが受けるので、`q:quit` も
  ペインのキーも**その画面では効かない**（「案内にキーを書いたら、その案内が出ている
  画面でそのキーが効くかを数える」。`.claude/rules/rust-coding.md`）。モーダルは箱の中に自前の案内を
  持っているので、同じことを 2 箇所で言わない。**1 行目の通知は残す** —— あちらは
  「何が起きたか」で、押せるかどうかと関係が無い。**空にするかを決めるのは
  `app::keys::live`** —— 「いま押せるか」は `update_key` の振り分けの話なので、
  `ui` で `modal.is_some()` を見ると規則の写しが 2 本になる
- **モーダル自身の案内は各モーダルが持っている**（`modals::*` の `HINT`。下の
  「モーダル」）。そのため**同じ動作に綴りが 2 通りある**（`[j/k] 選ぶ` と `j/k:移動`）。
  揃えないのは、あちらが箱の中で予算も文脈も違うから（#73 の「置かれる場所の予算が
  違うなら別の文言でよい」）。**表には寄せない**（`Modal::Help` のタスクで決めた）——
  `?` の一覧が出すのはペインとどこでも効くキーで、モーダルの中のキーはその箱が案内する
- **描くのは `message` の 1 行目だけ。** `git` の失敗ではそこに案内文が入り、argv と
  stderr は `detail` に退く（01 の「失敗の案内文」）。**案内文の予算は端末の幅から
  時刻の 9 セルを引いた残り**（80 桁なら 71 セル）—— ヒントが 2 行目へ移ったので、
  1 行目は時刻のほかは幅いっぱい使える。**進行中操作のバッジが出ているあいだは
  そのぶん短く切れる**（上の「進行中操作も 1 行目の先頭に」）
- **通知の前に積まれた時刻を `HH:MM:SS` で添える**（`ui::time::clock`、淡色）。日付は
  出さない（2026-09-26 にユーザーと決めた。1 行目の予算を日付の 11 セルで削らない）。
  **日をまたいだ通知は日付が判らない** —— 通知は入力でしか下ろさない（01 の「通知」）
  ので、23:10 の失敗が翌朝も `23:10:05` のまま出ていることがある。**受け入れた穴**で、
  日付は `L` の履歴で読む（下の「NoticeLog モーダル」）
- **溢れたら末尾を `…` にする**（`ui::ellipsize`）。黙って切ると、切れたことが画面から
  判らない。**予算を見張れるのは固定の文言だけ**で、パスやホスト名を埋めた文言には
  上限が無いので、そちらの受け皿
- **次の入力で下ろす**（01 の「通知」）。ステータスバーが描くのは
  `AppState::shown_notice` で、下ろした通知は出さない
- **キーの一覧は `app::keys` の 1 本。** `Modal::Help` と `config.keymap` の上書き（08）が
  同じ表を読む。2 本に分けると、上書きしたときにヒントだけが既定の字を出す。
  **表が持つのは実際の `Key`** で、`j/k` や `Enter` という字は `ui` が `KeyCode` から
  組む（表示の字を表にも書くと、導出できる値のコピーになる）
- **表は `update/*.rs` の `match key.code()` に対する 2 本目の一覧。** 嘘にならないよう、
  **表の全キーをそのペインで実際に押して、無反応でないことを見るテスト**を見張りに
  置く（`mewgit-core` の `every_hinted_key_does_something`）。**向きは表 → dispatch
  だけ** —— 逆（`match` の腕が全部表にあるか）は `match` から導けない
- **ラベルは git / `gh` の語をそのまま使い、画面の操作は日本語にする**
  （`s:stage` / `u:unstage` / `c:commit` / `C:amend` と、`j/k:移動` / `Esc:戻る` /
  `Enter:差分`）。**例外は `x:破棄`** —— `x:discard` にすると Worktree が 80 桁に
  収まらない（下の実測）。確認モーダルの見出し（「変更を破棄」）と同じ語なので、
  短くしたぶんで意味が薄れない

## モーダル

`Modal` の定義も 01 にある。

**モーダルを足すときに委譲する先。** 編集キーの共通部分は `update::edit_key`
（`update/mod.rs`。モジュールをまたいで使うので入口側にある）、**複数行の編集キー**は
`update::multiline_edit_key`、**1 つの欄だけの複数行入力の `Esc` / `Enter` の振り分け**は
`update::multiline_input_key`（`CommitMessage` と RebaseEditor の reword。`PrCreate` は
`Enter` の意味が欄で変わるので使わない）、**編集中バッファの描画と端末カーソルの配線**は
`modals::edit_area`（`CommitMessage` と `PrCreate` が使う。メッセージの箱ごと要るなら
`commit_message::render_editor`。RebaseEditor の reword が使う）。一覧から 1 つ選ぶモーダルは
`update::modal::picker_key` と `modals::picker`（#73 で寄せた）。**骨格に足せないキーは
包む** —— `AccountPicker` の `u` は `update::modal::account_key` が先に受けてから
`picker_key` に委ねる（`RemotePicker` には外す対象が無いので、骨格に置くと片方でしか
意味を持たないキーが増える。#78）。**確定して何をするかは各モジュールの側** ——
`Modal::Input` を組む `input` が `update/branches.rs` にあるのは、いまの利用者が
ブランチの作成とリネームだけだから（#75）。**貼り付け（`Msg::Paste`）の `match` は
網羅**なので、編集できるモーダルを足すとそこで選ばされる。
複数行の入力は `app::TextBuffer` で持つ。ratatui の
ウィジェットや `tui-textarea` を状態として持たない（core が UI に依存するため）。
`ui` は `TextBuffer` を毎フレーム `Paragraph` などに写して描く。

- モーダル表示中はキー入力をすべてモーダルに渡す。`Esc` で閉じる
- `Confirm` は破壊的操作の前に必ず使う（force push、`branch -D`、discard、abort 系）
- モーダルは画面の中央に、下のペインを覆って描く（`Clear` を敷く）。覆わずに重ねると
  下の文字が透けて読めなくなる。`Confirm` は「タイトル / 本文 / `[y] 実行  [n] やめる`」の
  3 段で、**本文には対象（パス）をそのまま出す**。「選択中のファイル」とだけ書くと、
  カーソルがどこにあるか思い出せないまま `y` を押すことになる
- **枠の高さは折り返し後の行数を実測して出す**（`ui::wrapped`）。折り返す本文を
  持つのは `Confirm` だけなので、`modals::place` は行数を受け取るだけにし、
  測るのは呼び出し側に置く（`CommitMessage` は折り返さないのでバッファの行数がそのまま）。`桁数 / 幅` の
  切り上げで見積もると、単語境界で折れて増えたぶんを数え落とし、本文の末尾が黙って
  切れる。枠には空行を 1 行取ってあるので 1 行の不足は吸われ、2 行足りないときに初めて
  見える。`contains` を見るテストはどちらでも通るので、**末尾がキーの案内より上に
  あることまで見る**。行数は ratatui の `Paragraph::line_count`（描画と同じ
  `WordWrapper` を通る）から取る。unstable feature `unstable-rendered-line-info` が
  要るので `mewgit-tui` の `Cargo.toml` で有効にしている
- **測る `Paragraph` を組むのは `ui::wrapped` だけ。** 測るときと描くときで `Wrap` の
  設定がずれるのを防ぐためと、枠（`block`）を付けたまま測らせないため。`line_count` は
  枠の上下を行数に足す一方、**枠の左右ぶんを幅からは引かない**ので、枠付きで測ると
  外側の幅で折り返した行数が返り、直したはずの「末尾が切れる」に戻る
- **枠の内側の右に 1 桁空ける。** ratatui の折り返しは**行が幅を超えるかを次の文字を
  足す前に見る**ので（`>=` 比較。`ratatui-widgets` 0.3.2 の `reflow.rs`）、最後の
  1 文字が全角だと行が `幅 + 1` セルで確定する。`Paragraph` は枠より後に描くため、
  **はみ出した 1 セルが枠の縦線を上書きしてその行だけ箱が開く**。1 桁空けておけば
  そこに落ちる（はみ出しが 1 セルで収まるのは、比較が `>=` なので最後の文字を足す前の
  幅が `幅 - 1` 以下だから）。**測るときと描くときで同じ幅を使う** —— 片方だけ空けると
  見積もりと描画がずれる。`Confirm` から在った形だが、実機で出たのは `gh` の
  `message`（全角と識別子が混ざる）を出す `AccountPicker` を入れてから
- **同じ穴はペインにもある。** はみ出すのは「枠付きの `Block` の `inner` に `Wrap` 付き
  `Paragraph` を描く」経路すべてで、`ui::pane_block`（padding を持たない）を使う
  CommitDetail のメッセージが同じ形（全角が混ざる代表）。**再現はしていない** ——
  ライブラリのソースで診断しただけ。**塞いだのは `ui::wrapped` の側**（`ui::WRAP_MARGIN`。
  M6 の「端末幅 < 100 のレイアウト（2/5）」）—— 折り返す `Paragraph` は全部
  `ui::wrapping` / `ui::wrapped` を通り、そこが右に 1 桁空けて測って描く。最初は
  `pane_block` に `Padding::right(1)` を足すつもりだったが、はみ出すのは折り返す描画だけで、
  ペインで折り返すのは CommitDetail の見出しとメッセージだけなので、**枠に載せると
  折り返さない Graph / Diff / 一覧まで 1 桁ずつ削る**（`/simplify` の altitude が拾い、
  2026-10-04 にユーザーと決めた）。**モーダルの枠（`modals::block`）が持っていた
  `RIGHT_MARGIN` は 4/5 で外した**（2026-10-04 にユーザーと決めた）—— モーダルの本文で
  折り返すものはどれも `ui::wrapped` を通るので、余白が 2 重（2 桁）にかかって 1 桁早く
  折れていた。外したので、箱の内側は `WIDTH` − 枠 2 になる（60 なら 58 セル）。見張りは
  `a_wrapped_line_that_just_overflows_keeps_the_border` で、**枠の記号ではなく内側の
  右端が空いているかを見る** —— `TestBackend` の `Buffer` では、はみ出した全角の 2 セル目に
  当たる枠の桁が `│` のまま残るので、枠を見ると余白 0 でも通った（実測 2026-10-04）
- **枠が食う幅と行数は `Block::inner` から出す。** `- 2` / `+ 2` と手で書くと、
  あとで `Padding` を足したときに折り返し幅だけが古いまま残る。高さは折り返してからで
  ないと決まらないので、幅の判る当て木（`Rect::new(0, 0, width, u16::MAX)`）を
  `Block::inner` に通して内側の幅と枠の行数を取る。グラフの詳細の見出しは枠を
  自分で持たないので、`inner.width` をそのまま渡す

## RemotePicker モーダル

```
   ┌ fetch するリモート ────────────────────────────────────────────────┐
   │ origin がありません（fork, upstream）。追跡先を設定してください    │
   │                                                                    │
   │ fork                                                               │
   │ upstream                                                           │
   │                                                                    │
   │ [j/k] 選ぶ   [Enter] fetch   [Esc] やめる                          │
   └────────────────────────────────────────────────────────────────────┘
```

- **`f` が既定リモートを決められないときだけ開く**（01 の「決まらないときの逃げ道」）。
  1 行目は**なぜ選ばされているか**で、`update::default_remote` が返した理由をそのまま
  出す。これが無いと、毎回出るのか設定が壊れているのかが判らない
- **カーソル行は `theme::selected()`**（ペインと同じ反転）。一覧から 1 つ選ぶ形は
  ペインと同じなので、見た目も同じにする
- **`Modal::AccountPicker` が 2 人目になったので、`modals::picker` に寄せた**（M4）。
  共有するのは**箱の中の割り方**（本文を `ui::wrapped` で測る → 空行 → 一覧を
  `Min(1)` で置く → `ui::render_rows` を通す → カーソル行を `theme::selected()`）で、
  各モーダルに残るのはタイトル・本文の文字列・行の組み立て・キーの案内だけ。
  **キー処理も同じ数え方で寄せた** —— `update::picker_key` が `j` / `k` / `Esc` と
  受けないキーを持ち、各モーダルが持つのは `Enter` で出す `Cmd` だけ（07 が
  「カーソル・キー処理・枠の描き方を寄せるかを数える」と送っていたうちの 2 つ目）。
  **閉じるかどうかも `Enter` の側**が決める —— `RemotePicker` は先に閉じ、
  `AccountPicker` は `submit_exec` を通すので落とされたときに閉じない
  **予告と違って行の型は問題にならなかった** —— 07 は「あちらの行は `GhLogin` の
  host / login / scopes なので `Vec<String>` には畳めない」と書いていたが、寄せたのは
  行の**組み立て**ではなく**置き方**なので、渡すのは組み立て済みの `Vec<Line>` で足りる
- **一覧が空でも呼べる。** `AccountPicker` は選ばせない degraded（`NoAccess` など）でも
  開き、そのとき渡す行は 0 本になる（04 の「内訳を出すのは `Modal::AccountPicker`」）。
  0 本のときは空行も一覧の領域も取らない —— `Min(1)` のまま呼ぶと一覧が 1 行を取り、
  **箱が端末の高さに丸められた回に本文の最後の行が消える**（実測の境目は 80x9 に
  内訳 5 件。**箱に余裕があるうちは `place` の余白から取るだけなので踏めない**）。
  消えるのはいちばん下 = 直し方の行
- 折り返さないので、`modals::place` に渡す行数は「本文の行数 + 空行 + 一覧の本数」。
  **本文は折り返しうる**ので `ui::wrapped` を通して測る（`Confirm` と同じ）
- **枠の中では一覧に先に行を渡す**（本文が `Max`、一覧が `Min(1)`）。本文を `Length` に
  すると、`modals::place` が箱を端末の高さに丸めたときに**一覧が 0 行に潰れる** ——
  リモート名が 1 つも出ないのに `j` と `Enter` は効くので、見えていない相手を fetch する。
  実機で測った境目は **30 本 × 80x14**（潰れる前は 0 行、直したあとは 1 行）。
  **`ui::render_rows` はここを守らない** —— あちらが守るのは「カーソルが一覧の外へ
  出ない」ことで、一覧そのものが消えることではない。しかも**理由はリモート名を並べる
  ので本数に比例して伸びる**（= 本数が増えるほど潰れやすい）

## AccountPicker モーダル

```
   ┌ GitHub アカウントを選ぶ ───────────────────────────────────────────┐
   │ アカウントを 1 つに絞れません（2 件）                              │
   │ 選ぶと .git/config の mewgit.user に保存します                     │
   │                                                                    │
   │ * taro_acme  repo, read:org                                        │
   │   taro  scopes なし                                                │
   │                                                                    │
   │ [r] 解決し直す   [j/k] 選ぶ   [Enter] 保存   [Esc] やめる          │
   └────────────────────────────────────────────────────────────────────┘
```

```
   ┌ GitHub アカウント ─────────────────────────────────────────────────┐
   │ 届いたアカウントがありません（3 件）                               │
   │ taro_acme: HTTP 403 で断られました                                 │
   │ taro: 確かめられませんでした（接続できませんでした）               │
   │ hanako: repo スコープが要ります（HTTP 404）                        │
   │   gh auth switch -h github.com -u hanako                           │
   │   gh auth refresh -h github.com -s repo                            │
   │                                                                    │
   │ [r] 解決し直す   [Esc] 閉じる                                      │
   └────────────────────────────────────────────────────────────────────┘
```

足りないスコープが判った候補には直し方を添える（04 の「権限不足の案内」）。
`gh auth switch` の行が出るのは、その login が gh の**設定上の**アクティブなアカウントでないとき（環境変数のトークンは数えない。04）。

決まっているアカウントを選び直す形（`Resolved`）。**一覧は `gh auth status` を
取り直して埋まる**ので、開いた直後は待ちの 1 行だけが出る。

```
   ┌ GitHub アカウントを選ぶ ───────────────────────────────────────────┐
   │ taro_acme @ github.com を使用（.git/config の mewgit.user）        │
   │ 候補を読み込んでいます…                                            │
   │                                                                    │
   │ [u] 指定を解除   [r] 解決し直す   [Esc] 閉じる                     │
   └────────────────────────────────────────────────────────────────────┘
```

```
   ┌ GitHub アカウントを選ぶ ───────────────────────────────────────────┐
   │ taro @ github.com を使用（設定ファイルの [[repos]]）               │
   │ 選ぶと .git/config の mewgit.user に保存します                     │
   │ 設定ファイルの [[repos]] は mewgit からは外せません                │
   │                                                                    │
   │ * taro_acme  repo, read:org                                        │
   │   taro  scopes なし                                                │
   │                                                                    │
   │ [r] 解決し直す   [j/k] 選ぶ   [Enter] 保存   [Esc] やめる          │
   └────────────────────────────────────────────────────────────────────┘
```

- **`A` で開く**（01 の「アカウントの選び直し」）。開くのは `Degraded` と `Resolved`
  の 2 つで、通知に落ちるのは `Resolving` だけ
- **選べるのは、候補が空でないときだけ。** `Ambiguous` と、取り直しが返った
  `Resolved` がそれに当たる。残りの degraded と、取り直しの待ち・失敗は内訳を
  **本文に**書き、一覧は空にする（`Enter` の効かない一覧を出さない）。
  **内訳を一覧側に置かない**のは、一覧が折り返さないため —— `Unusable` の `message` は
  1 行に収まらず、**このモーダルが在る理由そのものが右端で切れる**
- **タイトルと、キーの案内の `[j/k]` `[Enter]` は選べるかどうかで変わる**
  （`GitHub アカウントを選ぶ` / `GitHub アカウント`）。
  **同じ述語（候補が空か）から両方を出す** —— 別々に見ると、片方だけが
  「選べる」ふりをする。**待っているあいだだけは、候補が空でも「選ぶ」と書く** ——
  0.95 秒で候補が出るものを「選べません」と名乗って書き換えるほうが読めない。
  **引けなかったときは書き換える** —— あれは待てば変わる状態ではないので、選べる
  相手がいないことを枠でも言う
- **`[u] 指定を解除` を出すのは `AccountSource::GitConfig` のときだけ、
  `[r] 解決し直す` はいつも**（01 の「外で直したあとの再解決」）。
  `[u]` は**出す条件と、そのキーが効く条件が同じ述語から出る**（#53 の「案内にキーを
  書いたら、その案内が出ている画面でそのキーが効くか」）。**案内は
  `[u]` → `[r]` → 選ぶぶん、の順に並べる** —— 「その画面にしか無いキー」を先に置く
- **案内は箱の内側（`modals::WIDTH` 60 − 枠 2 = 58 セル。端末が狭ければそこまで縮む）に
  入らなければキーの区切りで折る**（下の「モーダルのキーの案内」）。`[u]` か `[r]` の
  どちらかに選ばせる案内を足すと 57 セル、**両方足すと 74 セルで 2 行になる**
  （`.git/config` 由来で候補が返った `Repick`）。見張りは**どの端末幅でも案内のキーが 1 つ残らず
  見えるか**を見る —— 折る前は 59 桁で末尾の `[Esc]` が切れていた（実測 2026-10-04。
  `[u]` を足す前は計算で 43 桁まで保っていた）。**`contains("[Esc]")` では浅い** —— 切れるのは
  行末からなので、5 セル溢れても `[Esc] やめ` が残って素通りする（実測）。`hint` が組んだ
  キーの群そのものと突き合わせる
- **`RepoRule` では本文の側に「mewgit からは外せない」と書く** ——
  **指示を足すのは、その操作を持たない側**（#65）
- **外での直し方が設定ファイルを指すなら、再起動が要ることも書く。** `r` が読み直すのは
  `gh` と `.git/config` で、**mewgit の設定ファイルは起動時に固まる**（08。`config` は
  `AppState` が持ち、`Cmd::ResolveAccount` はその写しを使う）。当たるのは `GhMissing` の
  `general.gh_bin` と `ConfiguredUnavailable` の `[[repos]]` の 2 つで、
  **`.git/config` の `mewgit.user` は毎回 git2 で開き直すので当たらない**
  （`gh` の入れ替えも、同じパスに置き直す形なら当たらない。どちらも pty で実測）
- **本文に保存先を書く**（`.git/config` の `mewgit.user`）。`f` が追跡設定を書かないのと
  同じ「黙って変えない」の裏返しで、**書くなら行き先を見せる**（01）。
  **`Resolved` では 1 行目に決め方も出す** —— `A` を押した人がまず知りたいのは
  「いま誰で、なぜそれになったか」で、ヘッダの `[gh: login @ host]` はそのうち
  「なぜ」を落としている（04 の表）
- **外での直し方は書いてよい**（`gh auth login`、`gh` の入れ替え）。#65 で決めた
  「指示を足すのは、その操作を持たない側」に当たる —— `RemotePicker` が
  「追跡先を設定してください」を書かないのは、あちらが**その操作を提供している**ため。
  `Ambiguous` の本文にだけは外での指示を書かない（選ばせるのがこのモーダルだから）
- **行に出すのは login と scopes、それに `LoginState`**（`Success` 以外のときだけ
  `gh: 応答なし` / `gh: 拒否`）。scopes が無ければ `scopes なし`。**gh の判定で候補を落とさない**と決めてある（04）ので、
  落ちた理由ではなく**選ぶ材料**として出す。`active`（`gh` の現在のアカウント）は
  行頭の `*` で出す

## Input モーダル

```
   ┌ ブランチを作成 (a1b2c3d から) ─────────────────────────────────────┐
   │ 新しいブランチの名前                                               │
   │ feat/x                                                             │
   │                                                                    │
   │ [Enter] 決定   [Esc] やめる                                        │
   └────────────────────────────────────────────────────────────────────┘
```

- 枠のタイトルが操作、その下の 1 行（`prompt`）が**何を打つのか**、その下が入力欄。
  **タイトルには対象も出す** — 作成はどのコミットから生やすか（`(a1b2c3d から)`。
  HEAD 起点のときは付けない）、リネームは元の名前（`prompt` が `main の新しい名前`）。
  `Confirm` の本文に対象をそのまま出すのと同じ理由で、押す前に読める必要がある
- **キーの案内は `[Enter] 決定   [Esc] やめる` で固定。** 操作名（作成 / リネーム）は
  枠のタイトルが言っているので繰り返さない。`Modal::Input` に案内の文言を持たせると、
  タイトルと 2 箇所で同じことを言い、片方だけ直った状態が生まれる
- **入力欄は折り返さない。** 折り返すと `ui` の出す桁とバッファの列が食い違い、
  カーソルの位置を出せなくなる（`CommitMessage` と同じ）。名前が幅を超えたときは
  カーソルの見えるところまで横にずらす
- **端末のカーソルを入力欄に置く**（`Frame::set_cursor_position`。`CommitMessage` と同じ）
- **箱を組むのは `modals::place`**（3 人目）。幅は `Confirm` と同じ。ブランチ名は
  コミットメッセージより短く、広く取る理由が無い
- **stash の push でも使う**（`z` / `Z`。01 の「stash の書き込み」）。タイトルは
  `stash（untracked を含む）`、1 ファイルなら `stash（<パス>）`。`prompt` は
  `メッセージ（空なら git の既定）`。**こちらは空で確定できる** —— 名前の入力は空を断る
  （`InputIntent::requires_text`）

## CommitMessage モーダル

```
   ┌ Commit message ────────────────────────────────────────────────────┐
   │ feat(app): コミットメッセージのモーダル                            │
   │                                                                    │
   │ Enter で確定する。改行は Shift+Enter か Ctrl-J。                   │
   │                                                                    │
   │ [Enter] コミット   [Shift+Enter / Ctrl-J] 改行   [Esc] やめる      │
   └────────────────────────────────────────────────────────────────────┘
```

- タイトルは `Commit message` / amend のときは `Commit message (amend)`。**どちらの
  操作をしているかを枠に出す。** amend は HEAD を書き換えるので、新規コミットのつもりで
  確定させない
- 中身は `TextBuffer` の行をそのまま並べる。**折り返さない。** 折り返すと、`ui` が
  出す桁とバッファの列が食い違い、カーソルの位置を出せなくなる。72 桁で折り返すのを
  勧める表示（`git commit` のコメント行に相当するもの）は入れない
- **端末のカーソルを本文の位置に置く**（`Frame::set_cursor_position`）。反転の升目を
  自前で描かない。編集中は端末側のカーソルが出ているのが自然で、`Confirm` のような
  「行を選ぶ」モーダルとは別物
- 高さは `Confirm` と同じく本文の行数から出す。**本文が枠より高くなったら下を切って、
  カーソルのいる行が見えるところまでずらす**（Diff ペインの窓と同じ形）
- キーの案内は最下行に、本文とは別に描く（`Confirm` と同じ理由。1 つの
  `Paragraph` にまとめると本文が伸びたときに押し出される）。**`Esc` は必ず出す。**
  確認を挟まずに本文が消えるので、押す前に見えている必要がある
- **箱を組むところは `Confirm` と共有する**（`modals::place`）。枠の測り方・高さの
  合算・`Clear`・本文とキーの案内への縦割り・中央寄せは、どのモーダルでも同じ。
  各モーダルに残るのは本文の作り方と幅と案内の文言だけ。2 つ目の利用者が出た時点で
  移す。写すと、余白や案内の位置を直したときに片方だけ古くなり、`contains` を見る
  テストはどちらでも通る
- **幅は `Confirm` より広く取る。** git のコミットメッセージは本文を 72 桁で折るのが
  慣習なので、そこが見えない箱だと折る位置を目で測れない
- キーの案内には `Shift+Enter` と `Ctrl-J` の両方を出す。`Shift+Enter` は端末が
  区別して送れるときだけ届き、`Ctrl-J` はどの端末でも届く（01 の
  「コミットメッセージの編集」）。片方だけ書くと、届かない端末の人に打つ手が無いか、
  届く端末の人が慣れたキーを見つけられない

## PrCreate モーダル

```
   ┌ Create pull request ─────────────────────────────────────────────────────┐
   │Title  feat(prs): N で PR を作る                                          │
   │Body   一覧から離れずに PR を出せるようにする。                           │
   │       base はリモートの HEAD から埋める。                                │
   │                                                                          │
   │Base   main                                                               │
   │Head   alice:feat  (1/2 <- ->)                                            │
   │Draft  [ ]                                                                │
   │[Enter] 作成   [Tab] 次の欄   [Space] draft   [Ctrl-J] 改行   [Esc] やめる│
   └──────────────────────────────────────────────────────────────────────────┘
```

- **欄は title / body / base / head / draft**。**ラベルの桁を揃えて左に並べ、値を
  右に置く。** `Body` だけが複数行で、ラベルの行から下へ伸びる
- **`Head` は選んでいる候補の `<owner>:<branch>` と、候補が 2 つ以上あるときだけ
  `(n/m <- ->)`。** 選び直すキー（`←` / `→`）は下の案内の行に足さず、この欄に
  置く —— 案内の行は既に枠の内側いっぱいで（下）、しかも**選び直せるのは候補が
  複数のときだけ**なので、効く場面でだけ出す。**矢印は ASCII**（`Draft` の
  `[x]` と同じく `ui::pick_charset` を通さずに済む）
- **どの欄に居るかはラベルの反転で出す。** 端末カーソルは編集中の欄に置く
  （`CommitMessage` と同じ）が、**`Head` と `Draft` には置けない** —— 文字を打つ欄では
  ないので列が無い。カーソルだけを手掛かりにすると、そこへ移った瞬間に**どこにも印が
  無くなる**
- **`Body` の行数は残りの高さから出す。** 箱の高さは 1 行の欄（`Title` / `Base` /
  `Head` / `Draft`）+ `Body` + `modals::place` が足す案内と枠。**算術で割る**（`ui::split` と
  同じ形）—— `Layout` の `Length` に絶対優先を与えると、狭い端末で `Body` が 0 行に
  潰れる（#65 で一覧を潰した形）。**0 行になったらカーソルを置かない**。
  **各欄の y は上から積む** —— `1 + body_rows` のように手で組むと、欄を足したときに
  その式が全部ずれる
- **折り返さない**（`CommitMessage` と同じ）。`ui` が出す桁とバッファの列が食い違うと
  カーソルの位置を出せなくなる。**窓の切り出しと横スクロールと端末カーソルの配線は
  `modals::edit_area` の 1 本**（`Input` / `CommitMessage` / この 2 欄が同じものを
  使う）—— #82 で「配線は `render` ごとに別」と結論したのは**2 箇所だったとき**で、
  ここで 4 箇所になったので寄せた。**ずらす幅はその欄の幅**（ラベルのぶん狭い）で、
  箱の幅ではない —— 渡す領域を測る側が決める
- **幅は `CommitMessage` と同じ 76。** 本文を書く箱なので `Confirm` より広い
- **案内の群のあいだは、ほかのモーダルと同じ空白 3**（74 セルで、枠の内側 74 セルに
  ちょうど入る）。`RIGHT_MARGIN` を外す前は内側が 73 セルだったので、ここだけ空白 2 に
  詰めていた。**4/5 で案内を群の並びで渡す形にした**ので、群を繋ぐ空白は
  `modals::place` の 1 箇所が決める（下の「モーダルのキーの案内」）
- **`Shift+Enter` は案内に出さない。** `CommitMessage` は両方出しているが、こちらは
  キーが 5 つ並ぶので予算が無い。**落とすのは `Shift+Enter` のほう** ——

- **`Draft` の値は `[x]` / `[ ]`。** `ui::pick_charset` を通さない —— ASCII だけなので
  端末で化けようがない
- **案内の上に空行は出ない。** `modals::place` が本文とキーの案内のあいだに取る 1 行は、
  高さを `Min(0)` で割るので**`Body` 欄に吸われる**（上の図はそれを写してある。

## NoticeLog モーダル

```
┌通知の履歴────────────────────────────────────────────────────────────────────┐
│2026-09-26 10:03:26 +0900 E ローカルの変更が上書きされるため切り替えられませ… │
│2026-09-26 10:03:26 +0900 W 変更のないファイルは stage できません             │
│2026-09-26 10:03:26 +0900 I fetch しました                                    │
│───────────────────────────────────────────────────────────────────────────── │
│ローカルの変更が上書きされるため切り替えられません。commit か stash           │
│してください                                                                  │
│                                                                              │
│git switch feat/x                                                             │
│error: Your local changes to the following files would be overwritten by      │
│checkout:                                                                     │
│        src/main.rs                                                           │
│                                                                              │
│[j/k] 選ぶ   [Esc] 閉じる                                                     │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **`L` で開く**（共通キー。どのペインでも効く）。**ステータスバーは要約行しか描かない
  ので、`detail`（argv と git の stdout・stderr）と日付が画面に出るのはここだけ**（01 の「通知」）
- **上が一覧、下がカーソル行の中身。** `j` / `k` で動かすと下が切り替わる。`Enter` で
  開く 2 段目を作らないのは、`j` / `k` だけで読み比べられるほうが、失敗が続いた
  ときに「どれが原因か」を探しやすいから（状態も 1 段で済む）
- **一覧は新しい順。** 行は `2026-09-26 16:13:03 +0900`（`ui::time::format`）と
  重さの 1 文字（`E` 赤 / `W` 黄 / `I` 淡色）と `message` の 1 行目で、溢れたら
  `…`（`ui::ellipsize`）。**重さを字でも出す** —— 色だけにすると、色の出ない端末で
  区別が消える。**下ろした通知も並ぶ**（下ろすのはステータスバーからだけ。01）
- **下は `message` の全文、空行、`detail` の全文を折り返して出す。** `detail` が無い
  通知は `message` だけ。**`message` を 1 行目で切らない** —— toml のパースエラーの
  ように複数行の案内がある（ステータスバーが 1 行目だけを描くのはこのため）
- **タブは Diff ペインと同じ規則で開く**（`ui::push_expanded`。8 桁のタブストップ、
  `\r` は落とす）。ratatui はタブを描かず、git の stderr は上書きされるファイルを
  タブで字下げして並べるので、開かないと字下げが消えて見出しと区別できない（上の図の
  `src/main.rs`。実物を描いて判った）。最初の版は空白 4 つの置換で、同じ git の出力を
  Diff ペインと 2 通りに描いていた（`/simplify` の reuse が拾った）
- **幅は端末に合わせて広く取る**（`modals::WIDTH` の 60 ではなく最大 100）。
  stderr は英語の長い行で、60 では 1 行が 2〜3 行に折れる
- **一覧に取る行数は内側の高さの半分まで**（`ui::capped_rows`。ペインの一覧と同じ
  規則）、残りを中身に回す。一覧を先に満たすと
  100 件のときに中身が 0 行になり、開いた理由（`detail` を読む）が消える。一覧は
  `ui::render_rows` でカーソル行が入るように窓を切る
- **中身が領域に入りきらなければ、最下行を `…` にする。** 黙って切ると、stderr の
  続きがあることが画面から判らない（ステータスバーの `…` と同じ理由）。**続きを
  スクロールして読む手段は無い** —— 受け入れた穴。git の失敗の stderr は数行に
  収まり、80x24 で一覧が半分を取り切っても中身に 10 行残る
  （`a_full_log_still_leaves_room_for_the_detail`）。**箱が端末の高さに丸められると、
  案内の上の空行も中身に回る**ので、`…` は案内の直上に来る
- **通知が 1 件も無くても開く**（本文に「通知はまだありません」）
- **開いているあいだに通知が積まれても、カーソルは同じ通知に留まる**（01 の「通知」）

## RebaseEditor

```
┌interactive rebase────────────────────────────────────────────────────────┐
│上から順に 1a2b3c4 の上へ積み直します。                                   │
│                                                                          │
│pick    a1b2c3d  Add feature                                              │
│reword  d4e5f6a  Fix the typo in README                                   │
│drop    789abcd  Update docs                                              │
│                                                                          │
│[p] pick   [r] reword   [e] edit   [s] squash   [f] fixup   [d] drop      │
│[j/k] 選ぶ   [J/K] 入れ替え   [Enter] 実行   [Esc] やめる                 │
└──────────────────────────────────────────────────────────────────────────┘
```

Graph の `i` で開く（01 の「interactive rebase の開始（`i`）」。範囲・断る形・reword の
入力のキーはそちら）。

- **上が古い順**（git の todo と同じ。グラフとは逆向き）。本文で「上から順に」と言う。
  **グラフと向きを揃えない** —— squash / fixup は「1 つ上の行に溶かす」なので、todo と
  逆に並べると溶かす先が下の行になり、git の語と画面の向きが食い違う
- `j/k` で選ぶ、`J/K` でカーソルの行を下 / 上と入れ替える（カーソルは行について動く）、
  `p/r/e/s/f/d` でカーソルの行を pick / reword / edit / squash / fixup / drop にする、
  `Enter` で実行、`Esc` でやめる（確認なし）
- **`r` はメッセージの入力に切り替わる**（下の図）。箱は `CommitMessage` と同じ形で、
  題に対象の短縮 Oid を出す。**一覧は隠す** —— 入力は複数行で高さが要り、並べると
  どちらも窮屈になる。`Enter` で決めると一覧に戻り、その行が `reword` になる。
  squash のメッセージは聞かない —— git が 2 本を空行でつないだものが入る
  （03 の「Interactive rebase の実装」）
- **reword の行の件名は、打ったメッセージの 1 行目を出す。** 行は「実行したらどうなるか」を
  見せる（drop を弱く出すのと同じ）ので、元の件名のままだと決めたメッセージが画面の
  どこにも残らない
- **検証は `RebasePlan::validate()` の 1 本。** 通らない plan（先頭の `drop` 以外が
  squash / fixup など）は本文の下に理由を赤（`theme::removed()`。通知の履歴の `E` と同じ）で出し、`Enter` は
  閉じずに同じ理由を通知にも出す。**描くたびに `validate()` を呼ぶ** —— 結果を
  `Modal` に持つと、行を動かすたびに更新を忘れる形が生まれる
- **全部 `drop` の `Enter` は確認を挟む**（`Modal::Confirm`）。git は通してブランチを
  `onto` まで戻す（03）
- **箱の割り方は `modals::picker`**（本文・一覧・窓の切り出し・カーソル行の反転）。
  行が箱に入りきらなければ `j/k` で窓が動く
- 行は `<動作><短縮 Oid>  <件名>`。動作の桁は最長の語（`squash` / `reword`）に揃える
  （`modals::rebase_editor::ACTION_CELLS`）。
  **drop の行は弱く出す**（`theme::muted()`。残らないコミット）
- **キーの案内は案内の行に全部並べ、2 行に折る。** 本文に凡例を置く形（#135）は
  やめた —— あれは 1 行の案内に収まらなかったキーの置き場で、意味で分けたものでは
  なかった（下の「モーダルのキーの案内」）
- **箱の幅は `CommitMessage` と同じ 76**（ほかのピッカーは `modals::WIDTH` の 60）。
  60 では使える幅が 58 セル（`RIGHT_MARGIN` を外す前は 57）で、動作の 6 キーの 1 行
  （68 セル）が折れて案内が 3 行になる。76 なら 74 セルで、1 行目 68・2 行目 57 セル
  （2026-09-30 に数え、2026-10-04 に余白を外して数え直した）。
  件名も長く見える。端末が狭ければ画面の幅まで縮む（`modals::place`）

```
┌reword d4e5f6a────────────────────────────────────────────────────────────┐
│Fix the typo in README                                                    │
│                                                                          │
│README の手順の綴りを直す。                                               │
│                                                                          │
│[Enter] 決める   [Shift+Enter / Ctrl-J] 改行   [Esc] 一覧へ戻る           │
└──────────────────────────────────────────────────────────────────────────┘
```

- **`Esc` は「やめる」ではなく「一覧へ戻る」と書く。** ほかのモーダルの `Esc` は閉じるが、
  ここは入力だけを捨ててエディタに戻る（01）

### モーダルのキーの案内

**そのモーダルで押せるキーは、案内の行（`modals::place` が箱の底に描く行）に並べる。**
書き方は `[キー] 動詞`。そのモーダルにしか無いキーを先に置き、`[Esc]` を末尾に置く
（`AccountPicker` の `[u]` / `[r]`、上の RebaseEditor）。

- **案内は文字列ではなく「行 → 群」の並び（`modals::Hint`）で渡す。** 群を空白 3 で
  繋ぐのは `modals::place` だけ。最初は 1 本の文字列を空白 3 の区切りで割り直す形に
  したが、区切りを守っているかを誰も見ない —— 空白 2 で並べた群は 1 つと読まれて
  折れずに切れ、群の中に空白 3 を書けばそこで割れる（`/simplify` の altitude が拾った）。
  フッターの `ui::hint_text` が `&[KeyHint]` を受けるのと同じ形
- **1 行に収まらなければ折る。** `modals::place` は箱の内側の幅を測り、入らない行を
  群の区切りで次の行へ送って（前から詰める）、その行数ぶん箱を伸ばす。本文へ押し出さない
  —— #135 の凡例は幅が足りずに本文へ移しただけで、書き方（`p:pick`）も置き場も
  案内の行と割れていた。**手で分けた行はそのまま行の切れ目になる** —— RebaseEditor の
  「動作の 6 キー」と「移動・実行」のように意味で分けた行は、幅が足りても混ぜない
- **折る前は、箱が端末の幅まで縮むと案内が右端で切れていた**（4/5。2026-10-04 に
  ユーザーと決めた）。最初に消えるのは末尾の `[Esc]` —— 確認を挟まずに閉じるキーで、
  押す前に見えている必要がある。境目は「案内のセル数 + 3」桁で、PrCreate は 73 桁未満、
  RebaseEditor は 71 桁未満、AccountPicker の `[u]` / `[r]` 付きは 60 桁未満で切れていた
  （実測）。**先頭から落として `[Esc]` だけ残す形は採らなかった** —— 狭い端末では
  `[u]` / `[r]` のような、その画面にしか無いキーが案内から消え、押せるのに知る手段が
  無くなる。**残る限界は群 1 つの幅** —— いちばん長い群（`[Shift+Enter / Ctrl-J] 改行`、
  27 セル）より内側が狭い端末（29 桁未満）では、その群が切れる
- **例外は、欄に紐づいて効く場面でだけ出すキー**（`PrCreate` の `Head` の `←` / `→`）。
  あれは候補が複数のときしか効かず、効く欄の隣に出すことで「どの欄に効くか」も言う

## ヘッダ

```
mewgit  owner/repo  [gh: user_shortcode @ github.com]  [api: 4984]   ⠋ fetch status
```

- **`[gh: …]` はアカウントが決まってから出す。** `AccountState::Resolving`
  （まだ頼んでいない / 走っている最中）のあいだは**何も出さない** —— 走っていることは
  右端のスピナー（`account`）が出しているので、左にも「解決中」を出すと同じことを
  2 箇所で言う。**`TargetState::Unavailable` のリポジトリでは永久に出ない**のもここ
  （GitHub のリポジトリとして特定できないので解決を頼まない。01）
- **`AccountState::Disabled` でも何も出さない**（`config.github.enabled = false`。
  01 の「GitHub 機能を切る」）。**「切ってあります」とも出さない** —— 自分で切った
  設定を毎フレーム言い返すことになるうえ、1 行しかないヘッダで `owner/repo` と
  スピナーの予算を食う。**`owner/repo` のほうは出し続ける** —— あれは `ssh -G` と
  リモート URL だけで決まり、GitHub API を叩かない（01）
- **見出しは `gh`。** 誰として GitHub に喋るかを出す欄で、その誰かを決めるのも
  トークンを出すのも `gh` CLI（04）。**理由の側で `gh` を繰り返さない**
  （`[gh: gh がありません]` にしない）
- **`Degraded` は `[gh: <理由>]` を `theme::warn()` で出す。** 理由は 1 行に収まる
  診断だけで、`NoAccess` の内訳（どの login がなぜ落ちたか）は出さない。並べる先は
  `Modal::AccountPicker`（04）
- **どの degraded にも `A` を添える**（`[gh: 1 つに絞れません（2 件）。A で選ぶ]` /
  `[gh: 実行できません。A で詳細]`）。**`A` が実際にそこで効くかを
  数えた** —— `A` は `f` / `p` / `P` と同じ共通キーで、どのペインからでも効く（#53 の
  「案内にキーを書いたら、その案内が出ている画面でそのキーが効くかを数える」）。
  **モーダル表示中は効かない**が、それは `A` に限らず全キーに掛かる一般則（上の
  「既定キーバインド」の末尾）。**キーヒントはそれに合わせて、モーダル表示中は 2 行目を
  空にする**（上の「ステータスバー」）。
  **選べない degraded でも案内する** —— ヘッダが 1 行に詰めて落とした内訳と外での
  直し方を出す画面は `AccountPicker` だけなので（04）、案内が無いと**出す先を
  用意したのに誰も辿り着けない**。文言が 2 つに割れるのは「押すと何が起きるか」が
  違うからで、判定は `DegradedReason::candidates()` の 1 本（選ばせる側と同じもの）
- **理由の文言は 1 行の予算に合わせて詰めてある**（`1 つに絞れません` /
  `どれも届きません`）。**`Modal::AccountPicker` は同じ事実を別の文言で書く** ——
  あちらは箱の中で折り返せるので詰める理由が無い。**揃えるとヘッダを 1 桁詰める
  たびにモーダルが痩せる。**
- **`owner/repo` と login が長くても `A` の案内は落ちない。** 幅が足りなければ下の
  「幅が足りないとき」の順に畳み、degraded は**リポジトリ名の次まで** `[gh: A で選ぶ]` /
  `[gh: A で詳細]` の形で残る —— ピッカーへ辿り着く唯一の手掛かりだから。リポジトリ名と
  キーの形が並ばない幅（`claude-code` なら 41 桁以下）では消える。**5/5 より前は**
  `microsoft/vscode-python-debugger`（31 桁）で幅 100 でも案内が切れていた
  （実測。右端のスピナーに食われるまま切れていた）
- **`owner/repo` は `RepoInfo.target` が決まったときだけ出す。** 既定リモートが無い / URL を
  GitHub の形として読めないリポジトリではリポジトリ名だけになる（01 の
  「`RepoInfo.target` を埋める」）。**起動直後の 1 フレームにも出ない** —— `ssh -G` の
  往復を挟むので、リモート一覧が届いたあとに 1 テンポ遅れて現れる
- **`[api: …]` は GitHub API の残量**（`core` バケットの `remaining`。05）。
  **1 度でも応答が届いたら出し続ける** —— 閾値を割ったときだけ出す形は、**出ていない
  あいだ減り具合が見えない**。一覧 1 本と PR ごとの扇形で 1 回の引き直しに 100 往復を
  超えることがあり（05 の実測）、出たときにはもう遅い。**乏しいとき（上限の 10% 以下）
  だけ `theme::warn()`** で、割合で見るのは上限がトークンの種類で変わるから
- **上限は添えない。** `[api: 4984/5000]` は 18 セルで、そのぶん残量が先に落ちる
  幅が広がる（下の「幅が足りないとき」の 3 段目）
- **`[gh: …]` の degraded とは同時に出ない。** degraded では `PrState::forget` が
  残量を落としており（残量は**そのトークンの予算**。01）、`Resolving` では一度も
  引いていない。**残量が出る隣はいつも `[gh: login @ host]`**
- **入らなければ出さない。** はみ出した `[api: 4984]` は `[api: 49` のように**桁の減った
  数がそのまま読める**ので、切らずに丸ごと落とす（下の「幅が足りないとき」の 2 段目）。
  **5/5 より前は残量だけが自分で譲っていた** —— スピナーを左群に重ねて描いていたので、
  門はそのフレームのスピナーの幅を引き、左群 70 セルでは幅 85〜95 で**扇形
  （`pr checks`）が走っているあいだだけ残量が消え、終わると出る**帯があった
  （実測 2026-09-18）。そのときの境目の表は次のとおり（扇形のスピナー 11 セルが走っている最中）——

  | 左群 | 出るのに要る幅 | 切れた数が読める幅 | 数は全部出るが門が断る幅 |
  |---|---|---|---|
  | `mewgit  yshrsmz/mewgit  [gh: yshrsmz @ github.com]`（50 セル） | 76 | 70〜72 | 73〜75 |
  | `claude-code  anthropics/claude-code  [gh: user_shortcode @ github.com]`（70 セル） | 96 | 90〜92 | 93〜95 |

  **スピナーの席を常に取るようにして帯は消えた**（下の「幅が足りないとき」）
- **走っているものがあるときだけ出す。** 出しっぱなしだと「何か動いている」の意味が消える
- **`Tick` を 1 つまたいで走っているジョブだけを描く**（`Job::since` は発行した時点の
  `AppState.tick`）。2 秒ごとの probe（1ms 未満）と小さなリポジトリの定期の status は
  1 フレームで終わるので、描くとそのたびに駒と説明が 1 フレームだけ光り、`[api: …]` が
  その幅を譲って消える（01 の「外部の変更の検知」）。大きなリポジトリの遅い status は出る。
  **出るまで最大 1 周期（250ms）遅れる**のは受けた
- **駒は `AppState.tick`（`Msg::Tick` の回数）の剰余で選ぶ。** 時刻を読まないのは、
  `render` が `AppState` だけを見る（不変ルール 2）ようにするため。`jobs` の中身で選ぶと、
  走っているものが変わらないあいだ止まって見える
- **駒と一緒に説明も出す**（`Job.label`。`Exec` は `fetch` / `push` のように走らせる
  サブコマンド）。01 の「スピナー」に、どこで入れているかがある
- **右端の 13 セルはいつもスピナーの席**（`ui::SPINNER_SEAT`。左群とのあいだの区切り 2 を
  足して 15 セル）。何も走っていなくても空けておく —— 走るたびに左群の予算が変わると、
  境目の幅でジョブが出入りするたびに `@ host` や `[api: …]` が出たり消えたりする
  （定期の status でも起きる）。13 は `⠋ cherry-pick` が入る幅で、**席に入らない説明は
  畳む** —— 入るだけ並べて残りを `+N` にし（`⠋ fetch +2`）、1 つも入らなければ
  `⠋ +3`、1 つしか無いのに入らなければ切る。**ラベルの長さを席に合わせる見張りは
  置かない**（畳めるので、長いラベルを足しても崩れない）。
  **代償はアイドル中の 15 セル** —— 左群 50 セル（`mewgit  yshrsmz/mewgit  [gh: yshrsmz @ github.com]`）
  では、`[api: …]` まで全部の形が出る幅がアイドルで 65 → 78 桁、`pr checks` が走って
  いるあいだは 76 → 78 桁になった。**`[api: …]` そのものは変わらず 65 桁から出る**
  （`@ host` を落とした段が先に入る。`/code-review` が測った。2026-10-05）。**ヘッダの領域は `ui::render` が左群・区切り・席の 3 つに
  割る** —— 左群は席に掛かれない（予算の算術ではなく領域で止める）
- **右端に置くのは、動くものに固定席を与えるため。** #56 が記録していたのは「ステータス
  バーから追い出した」ことだけで、**なぜ右端かは書かれていなかった**ので、他の TUI を
  実機で撮って数え直した（2026-09-19、いずれも幅 100）。

  | | 一時的な表示 | 置き方 |
  |---|---|---|
  | lazygit 0.65.1 | `Fetching ∙●∙` | ステータス行の**左端に固定**し、後ろのキーヒントを押し出す |
  | gitui | `⣷` 1 セル | **左上隅に固定**（`ESC[1;1H`。タブ見出しに重ねる） |
  | tig | 位置と進行の `100%` | タイトル行の**右端に固定** |

  置き場所は 3 本ともばらばらだが、**固定席を与えている点は同じ**で、可変長の内容の
  うしろに流している例は無かった。**「全部左寄せにしてスピナーを最後に置く」案は
  この理由で採らない** —— 動くものの席が左の中身で動くうえ、**狭いときに最初に
  切れるのが「動いている」の合図**になる（HTTP は最長 30 秒待つ）。
- **`[api: …]` を左群に置くのは、それが `[gh: …]` の予算だから。** 右端は上のとおり
  一時的なものの席で、残量は**そのトークンに紐づく値**（アカウントを切り替えると
  一緒に消える。01 の「PR ペイン › 残量」）。右端へ寄せて「スピナー + 残量」を
  1 本の右寄せ行にする案も測ったが、**同じ行に性質の違う 2 つを並べることになる**ので
  採らなかった
### 幅が足りないとき

**左群は「幅 − 15」に入る最初の段で描く**（2026-10-05 にユーザーと決めた。M6 の
「端末幅 < 100 のレイアウト（5/5）」）。上から順に試す ——

1. 全部（`mewgit  owner/repo  [gh: login @ host]  [api: …]`）
2. `@ host` を落とす（`[gh: login]`）。degraded は理由ごとそのまま
3. `[api: …]` を落とす
4. `owner/repo` を落とす
5. degraded の理由を落としてキーだけにする（`[gh: A で選ぶ]` / `[gh: A で詳細]`）。
   解決済みの `[gh: login]` はここで落とす
6. リポジトリ名（ディレクトリ名）だけ。それも入らなければ `…` で切る（幅 15 以下では
   左群に 1 セルも残らず、スピナーの席だけになる）

- **`owner/repo` を `[gh: …]` より先に落とす。** リポジトリはたいていディレクトリ名で
  分かり、`[gh: …]` は degraded のとき `A` への唯一の手掛かり。**代償** —— fork や別名で
  clone したリポジトリでは、幅 70〜90 で（左群の長さによる）どのリモートか分からなくなる
- **`@ host` を最初に落とす。** たいてい `github.com` で、落としても誰かは分かる。
  **代償** —— GHES と github.com に同じ login があると区別できない
- 試算（左群 `claude-code  anthropics/claude-code  [gh: user_shortcode @ github.com]` の 70 セル）——

  | 幅 | 解決済み | degraded（`Ambiguous`） |
  |---|---|---|
  | 100 | 全部 | 全部 |
  | 90 | `claude-code  anthropics/claude-code  [gh: user_shortcode]  [api: 4984]` | `claude-code  [gh: 1 つに絞れません（2 件）。A で選ぶ]` |
  | 80 | `claude-code  anthropics/claude-code  [gh: user_shortcode]` | 同上 |
  | 70 | `claude-code  [gh: user_shortcode]` | 同上 |
  | 60 | 同上 | `claude-code  [gh: A で選ぶ]` |

- **5/5 より前は落とす順序が無く**、`owner/repo` と `[gh: …]` は右端のスピナーに食われる
  まま切れていた —— 80 桁では `anthropics/claude-code` + `user_shortcode` と `pr checks` の
  スピナーで `[gh: …]` の閉じ括弧が消えた（実測 2026-09-18）

## 見えない行の組み立て

**一覧と diff は、窓に入る行だけを組む**（`ui::render_rows`。M6 の「端末幅 < 100 の
レイアウト（3/5）」で塞いだ）。描画は入力が無くても `Tick`（250ms）で回るので、1 秒
あたり 4 回。それまでは全行を組んでから窓の外を捨てており、`ui::file_row` は 1 行
あたり `String` を 2 つ確保するので、依存の更新のような 500 ファイルのコミットに
カーソルを置くと、毎秒 2000 行ぶんを組んでその大半を捨て続けていた。

- **`render_rows` は行の数と、添字から 1 行を組む関数を受ける。** 窓を先に決めて、
  その中の添字だけを呼ぶ。ペインに `ui::window` を直接使わせるのは、その戻り値の
  使い方が各ペインに写るので採らない（`render_rows` の doc）
- **見出しを挟むペイン（Worktree・Diff・CommitDetail のファイル一覧）は、描く行の軽い
  記述を先に 1 回で並べる。** 見出しか、どの `FileEntry` か、どのハンクの何行目か ——
  借用だけで `String` を持たないので全行ぶん並べても安く、`len` とカーソルの行を同じ
  走査で出せる。**添字の規則を 2 本にしない**ため（数え直すと、反転する行と窓の基準行が
  静かにずれる）。並べること自体は行数ぶんの走査として残る —— 記述を並べずに添字から
  (ファイル, ハンク, 行) を引けば窓の高さぶんで済むが、ペインごとに添字の算術が要るので
  採らなかった（`/simplify` の efficiency が挙げた。`String` を組まないぶんで足りる）
- **全部組む一覧も残る**（`ui::render_built`）。右上のタブは割く高さを行数から出し、
  PRs は桁の幅を一覧ぜんぶから決める。picker と通知の履歴の一覧は本数に上限がある
  （候補・通知 100 件）。どれも組まずに数を出す形にすると、数える規則が 2 本になる

**`NoticeLog` モーダルの中身は「描ける行 + 1 行」で打ち切る。** 中身は長さに上限が
無い（hook の出力をそのまま運ぶ）ので、全文を組んで折り返しを測っていた。元の 1 行は
折り返して 1 行以上になるので、**元の行で数えて端末の高さ + 1 行まで取れば**、溢れたかの
判定（`…`）も箱の高さも変わらない。**1 行が極端に長い形（改行の無い 1MB）は打ち切らない**
—— 元の行の数で切るので、その 1 行は全部組んで測る。実測（2026-10-04、release、120x40、
200 回平均、同じ手順で前後を並べた）—— detail 5000 行で **1.78ms → 133µs**、100 件で
detail 2 行なら 281µs → 251µs（一覧の 100 行は組み続ける）。2026-09-26 に測った 7.1ms は
別の手順の数で、比べるなら同じ日の 1.78ms のほう

## 描画の原則

- `render` は `&AppState` のみ参照する
- 長い一覧は `ratatui` の `ListState` / 自前 viewport で可視範囲だけ描画
- 色は `theme` 構造体経由で参照し、直接 `Color::Red` を書かない。文字列から
  `Style` への変換は `ui::theme::style`（08 の「スタイル指定」）。ペインごとに
  持たない
- 進行中ジョブがあるときはヘッダ右端にスピナー（上の「ヘッダ」）
